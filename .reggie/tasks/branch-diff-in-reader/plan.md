# Show what a task changed, line by line, inside the reader; no route returns a hunk anywhere today

## Problem
Reggie's stated job is to let the repo owner review what changed and why, and it cannot show one changed line. Every `git diff` call in the product is name-only or stat: `branchChangedFiles` in `tasks.ts` feeds the "changed on branch" chip, `completionDiff` in `serve.ts` sums a merge's numstat for the Completed view, and `diffStat` pastes a stat block into a packet. The reader drawer renders one numbered row per source line, but only ever from the working tree of the serving checkout, so opening a changed file from a task page shows the file as it was before the change. To read a change Jacob leaves the page for a terminal, and with low-risk completions now passing by policy that is where most of his review would have to happen: after the work has landed.

The brief sketches the fix as splicing deletion rows into the branch-side text of the file. Measured against this repo, that sketch would hide more than a third of what it is meant to show. `/api/file` cuts a file at 20,000 characters, which falls at line 475 of `serve.ts` (2,288 lines), 437 of `board.js` (3,152), 529 of `app.js` (2,685) and 473 of `story.ts` (2,909). Across the last twelve landed tasks, 126 of 342 hunks in non-record files start past that cut, and 50 of 130 changed files have at least one hunk behind it.

The second measured fact is about where the diff is hosted. The brief settles on the file page, with the task page as the door. A file page asks three routes about its path, and for any path the code map never read all three answer 404: measured on a probe server, `/api/story?scope=file`, `/api/impact?id=` and `/api/explain?id=` each answer 404 for `.reggie/tasks/intake-line-leaves-at-triage/packet.md`, while `/api/file` reads it. That is every one of Reggie's own records, every file a live branch adds, and every file a landed task deleted. It is not a corner: of the 64 files the last merge landed, 39 are under `.reggie/`, and the owner has ruled that those are listed with the same hunk view.

The third is that every real hazard sits in degenerate input, and git's text output is full of it. All of the following was measured on git 2.55 in throwaway repos before this plan was written:

- **Deleted file**: patch carries `deleted file mode`, `+++ /dev/null` and one hunk `@@ -1,2 +0,0 @@`; numstat `0 2`; `git show <ref>:<path>` exits 128, so there is no branch-side text.
- **Added file**: `new file mode`, `--- /dev/null`, `@@ -0,0 +1,2 @@`.
- **Rename without edits**: `similarity index 100%`, `rename from`, `rename to`, no `index` line, no hunk; numstat `0 0`.
- **Rename with edits**: `similarity index 85%` and one hunk. Asked for by its new path alone, git reports the same file as wholly new, all ten lines added; the rename is only seen when the old and the new path are both given.
- **Binary file**: `Binary files a/src/blob.bin and b/src/blob.bin differ`, no hunk; numstat `- -`; a new binary reads `Binary files /dev/null and b/… differ`.
- **Mode-only change**: `old mode 100644`, `new mode 100755`, nothing else; numstat `0 0`.
- **Empty file**: an added empty file is a header with `new file mode` and `index`, and no `---`, no `+++`, no hunk; a file emptied on the branch is `@@ -1 +0,0 @@`; an empty file that gains a line is `@@ -0,0 +1 @@`. The count after the comma is omitted when it is one.
- **No trailing newline**: `\ No newline at end of file` follows the row it describes, once per side, so an edit to an unterminated line carries the marker twice in one hunk.
- **Odd paths**: with git's default quoting a name with an accent prints as `"src/caf\303\251 \303\274.ts"`, quote marks included. `core.quotePath=false` fixes the accent and nothing else: a name with a quote mark or a tab is still C-quoted in the patch header and in text numstat. A name with a space gets a tab appended on its `---` and `+++` lines. A file really named `src/a => b.ts` prints unquoted in text numstat, byte-identical to a rename. Only the `-z` forms are unambiguous: a rename there is `1<TAB>1<TAB><NUL>old<NUL>new<NUL>`.
- **A path beginning with a dash**: without `--` git reads `-leading-dash.ts` as options and exits 129; with `--` it is a path. A revision argument beginning with a dash is worse: `--output=/tmp/x...task/demo` made git try to open that file for writing.
- **Pathspec magic**: a path argument of `:(exclude)src` returned the stats of other files, and `src/*.bin` matched two files; under `git --literal-pathspecs` both matched nothing.
- **Content that imitates diff syntax**: a deleted line whose text is `-- a/old.ts` prints as `--- a/old.ts`, byte-identical to a file header. An added line reading `@@ -9,9 +9,9 @@ fake` or `\ No newline at end of file` is safe only because its `+` comes first.
- **The user's own git settings**: `color.ui=always` wraps every line in escape codes; `diff.external` ran the configured program in place of the patch; `diff.noprefix` dropped `a/` and `b/`; `diff.context=0` changed the hunk count from 1 to 2; `diff.renames=false` reported 0 renames where `-M` reports 2.
- **CRLF**: every patch line of a CRLF file ends in a carriage return. **Symlink**: mode `120000`, its one line is the target, with the no-newline marker.
- **Zero commits past the base**: the range is empty and git exits 0. **Only `.reggie/` changes**: two files, both records.
- **A branch that merged the base back in**: the diff from the merge base names only the branch's own file (`2 1 src/a.ts`). The tip-to-tip diff drags in two files the branch never touched, and the union of the branch's commits includes the merge's first-parent diff, `src/b.ts`, which is the base's work and not the task's.
- **A branch that changed a line and changed it back**: two commits ahead, an empty diff.
- **A very large patch**: a 60,000-line added file is one hunk, 889,026 bytes and 60,006 lines of patch; a 5 MB single-line file is 8 lines of patch; the whole branch is 5.9 MB. Git answers each in about 20 ms, so the cost is the payload and the rows a browser would have to draw, not git.
- **A done task whose branch is deleted**: `main...task/landed` fails with exit 128. The merge Reggie made is found on the base's first-parent line, and its diff against its first parent is what landed: the file, plus the packet with `verdict: approved`, which was written inside the merge commit, where the branch alone still says `pending`. The base had moved on since, so the text at the merge has 3 lines where the serving checkout has 4.
- **A done task landed by fast-forward**: no merge commit and no branch. Nothing but commit trailers says which commits were its.
- **A slug with no branch at all**: exit 128. **Unrelated histories**: `fatal: … no merge base`, exit 128. Both are silent under the existing helpers' `allowFailure`, which would make a failed read indistinguishable from "nothing changed".

## Approach
Read a task's change as one range of two full commit shas, list it from git's null-separated output, fetch one file's patch at a time, and build the rows the reader draws on the server, where they can be tested.

**The range.** `tasks.ts` already knows which ref a task's branch is (`refFor`), so `TaskInfo` gains one additive field, `branchRef`: `task/<slug>` when the branch is local, `origin/task/<slug>` when only the remote-tracking ref exists, `null` otherwise, and never a `plan/` branch. A new `taskRange` in `changes.ts` turns a task into a range in this order. A task that is not done and whose branch is ahead of the base reads from the merge base to the branch tip, which is the three-dot diff `branchChangedFiles` already uses and is exactly what a merge would land. Otherwise, when `taskLanding` from `history.ts` (the merge-commit lookup `task-attribution-by-merge` landed) finds a merge with two parents, the range is the merge's first parent to the merge. Otherwise a branch that still resolves is read from its merge base, which covers an approved task that was squashed elsewhere and a branch with zero commits past the base. Otherwise there is no range, and the answer says why in a sentence of Reggie's own. Every name is resolved once to a 40-hex sha, and only shas are handed to the diff helpers.

**The list.** `git.ts` gains `diffRawRange` and `numstatRange` beside `diffStat` and `changedFiles`, and `patchFor` for one file. All three pin what the user's settings could otherwise change: `git --literal-pathspecs -c core.quotePath=false diff --no-color --no-ext-diff --no-textconv -M`, revisions after `--end-of-options`, paths after `--`. They return `null` when git fails or times out (10 s) and `""` when nothing changed, so the two are never confused. Their argument arrays come from one exported builder, the way `historyLogArgs` builds the history log's, so a test can read exactly what git is handed. `changes.ts` parses `--raw -z --no-abbrev` for status, modes, blob shas and both paths, and `--numstat -z` for counts and the binary marker, and joins them by path. Entries under `.reggie/` go to `records`, everything else to `files`, and the totals count `files` only, which is the owner's ruling. What is reused rather than rewritten: the `.reggie/` rule, `taskLanding`, `isSafeSlug`, `safeRepoPath`, `qInt`, and the `git()` argument-array runner. What is deliberately not reused is `parseNumstatPath`, because the text form it parses cannot tell a file named `a => b` from a rename.

**One file.** `fileDiff` first finds the path in that list by exact match; a path that is not in the list never reaches git. For a rename it passes the old and the new path together. The patch parser ignores every path in the header, since the list already knows them, and reads hunks by count: the `@@ -a,b +c,d @@` header says how many old and new lines follow, so a deleted line that looks like a file header is consumed as the deletion it is. The no-newline marker becomes a flag on the row before it and is never a row, so new-side numbering cannot drift. Trailing carriage returns are dropped for display, as the reader already does.

**Rows, not text.** `diffRows` turns hunks into the rows the reader draws: `ctx`, `add` and `del` rows carrying their old and new line numbers, and a `gap` row between hunks saying how many unchanged lines are not shown, computed from the hunk headers and, for the tail, from the new blob's line count. A change at line 1,500 is therefore as reachable as one at line 5. The response carries at most 2,000 rows from `offset`, each row's text cut at 2,000 characters with `cut: true`, with `totalRows` and `truncated`, and the reader offers the next page. Cases with nothing to draw answer with a `card` instead: `binary` with both byte sizes, `mode`, `renamed`, `empty`, `symlink`, `deleted` (above the deleted lines), and `unreadable` when git failed or the patch outgrew the buffer. For a merge range the payload also says `changedSince` when the file's blob at HEAD is no longer the one that landed, because the row numbers are then the landing's and not the working tree's.

**The reader.** `reader.open(path, { diff: slug })` fetches `/api/filediff` instead of `/api/file` and renders the rows with the same DOM it uses today: one `.reader__line` per row, the new-side number in the existing gutter, a sign column carrying `+` or `−` so colour is never the only signal, a tint on added and deleted rows, and an unnumbered, unselectable gap row. Rows that have a new-side number keep `data-line`, so `scrollTo`, the line highlight, select-to-note and the editor link keep their meaning; deleted rows have none, and a selection that ends on one offers no note. The note prefill names the task, because the numbers are the branch's and not the checkout's. Symbol marks are dropped in diff mode. The reader's identity becomes the path plus the diff slug, so flipping modes reloads. A head button flips between the change and the file as it is now, through a dep that rewrites `?diff=` on the route. The editor link points at the task worktree's copy when `.worktree/<slug>/<path>` exists, at the serving checkout's copy for a landed task, and is hidden otherwise, since opening the unchanged file at the branch's line numbers would mislead.

**The door.** The file route carries `?diff=<slug>`; `parseRoute` and `formatRoute` already round-trip a query. With it set, `app.js` always opens the reader, on a phone too, where the reader opening already brings up the map overlay. When the story answers 404 in diff mode the story column says in words that the file is not part of the code map in this checkout and why, in place of an error card, the map's failure toast is not raised, and the canvas is cleared of the previous page's graph. The actions row gains a link back to the task. A symbol link clicked in diff mode is left to navigate normally, which lands on the plain file with the symbol highlighted. On the task page `board.js` adds one section, "What changed", filled from `/api/changes`: a summary line naming the range, a row per file with a status badge, the door and its counts, then "Reggie's own records" under its own heading with the same doors. Once the list arrives, any "Files to touch" row and any "also changed" link whose path is in it becomes a door as well; the list is the one source of doors, so a done task, whose `impact.actual` is empty, gets them too. In the Completed view each "Files changed" link becomes a door when the task has a landing merge, and the sentence about records points at the task page.

Rejected alternatives. Splicing into the full branch-side text, as the brief sketched: measured above, the 20,000-character cut would hide 37% of real hunks, and raising the cut moves the problem to the browser. Parsing one whole-branch patch and splitting it by file: it needs the header paths, which is where the quoting, the appended tab and the `a => b` ambiguity live, and the large case is 5.9 MB per request. Building the rows in `reader.js`: nothing under `ui/` has an automated test, and the row arithmetic is where the degenerate inputs bite. The union of the task's own commits as the range: measured above, it attributes the base's work to a branch that merged the base back in, and shows work the branch itself undid. Hosting the reader on the task page: it would make every file behave alike, but the brief names the file page, a diff there has an address that survives a reload, and the pane logic assumes code belongs to file pages; the unmapped-file case is handled where it occurs instead. A `reggie diff` verb or an MCP tool: out of scope by the brief.

## Assumptions
- Done tasks are in scope, through the merge-commit lookup. Answered by jacobpress on 2026-09-15 in the brief, which also withdraws the "Not this" line that excluded them; binding. The lookup is `taskLanding` in `history.ts`, reused as it stands. Measured: the merge's diff against its first parent is what landed, including the verdict written inside the merge.
- Reggie's own records are left out of the counts and of everything that feeds impact and the map, and are listed under their own heading with the same hunk view. Answered by jacobpress on 2026-09-15 in the brief; binding. `impact.actual` and `changedFiles` are untouched, so the map and the blast radius see exactly what they saw before.
- The range for a live branch is the diff from the merge base, not the union of the task's own commits. The brief leaned this way without deciding. Measured: for a branch that merged the base back in, the merge-base diff names the branch's one file, while the union of its commits adds the base's file through the merge's first-parent diff; for a branch that undid its own change the union shows work that will never land. The merge-base diff is also what `branchChangedFiles` computes, so the chip and the list agree. Rejected: the union of commits.
- The cut applies to the patch, not to the file, and the paging unit is 2,000 rows by `offset`. Measured: the largest single-file change in the last twelve landed tasks is 563 added and deleted lines, an evidence file, and the largest in product code is 416, so one page covers every real file seen so far, while the 60,000-line case needs 30 pages and stays under a megabyte each. Rejected: the brief's full-text splice under the 20,000-character cut, which hides 37% of real hunks; also rejected: no paging at all with a pointer to the terminal, because the owner's earlier sketch said hunks are paged and the server side of it is a slice.
- Unchanged stretches are collapsed into a gap row that cannot be expanded. The mode button shows the whole file, and for a live branch the unchanged lines there are the same lines. Rejected: expandable gaps, which need a second route or the whole blob in the payload.
- Symbol marks are dropped in diff mode, not recomputed and not shifted. They are computed from the serving checkout's text, the rows are the branch's, and a mark on the wrong line is worse than none. A symbol link clicked in diff mode navigates normally and lands on the plain file with the symbol highlighted. Rejected: running the symbol scanner over branch text, which would put `symbols.ts` and the graph into a route that otherwise touches neither.
- A file page opened without `?diff=` stays in plain mode and offers nothing about tasks beyond what it shows today. The doors are on the task page and the Completed view, where the task is already named. Rejected: offering the tasks whose branches touch the file, which means resolving every live branch's change list on every file page; and picking the newest, which guesses.
- Team mode never fetches. `branchRef` names `origin/task/<slug>` when that is the ref the clone has, and the range is read from it; a branch that is in no ref of this clone has no range and the answer says so. Checked in the code: such a branch is invisible to the state derivation too, since `listBranches` reads local and `origin` refs only. Rejected: a fetch inside a GET, because this server answers one request at a time and a network call would hold every other request.
- The diff is reachable from the "What changed" rows, from "Files to touch" rows and "also changed" links whose path is in the change list, and from the Completed view's file links. File links inside plan prose stay plain, because prose names a file and not a change. No new key: S, M and C fold panes and the diff is not a pane; the mode button is the only switch.
- The rows are built on the server. Nothing under `ui/` has an automated test, and the last run's bugs all sat in degenerate inputs, so the arithmetic lives in `changes.ts` under vitest and the reader only draws what it is given. Rejected: parsing the patch in `reader.js`.
- The patch is requested one file at a time with the paths taken from the null-separated list, and the parser never reads a path out of a patch header. Measured: header paths are C-quoted even under `core.quotePath=false`, carry an appended tab when they hold a space, and lose `a/` and `b/` under the user's `diff.noprefix`. The brief suggests reusing the numstat parser in `history.ts`; this plan reuses its `.reggie/` rule and `taskLanding` and not `parseNumstatPath`, because the text form cannot tell a file named `a => b` from a rename. That bug in the history reader is captured, not fixed here.
- A revision never comes from the query string. Branch names are built from a slug that passed `isSafeSlug`, which cannot start with a dash or hold a slash, a dot or a colon; each is resolved once with `rev-parse --verify --quiet --end-of-options <name>^{commit}`, and only a value matching 40 lowercase hex characters is handed on. Merge and parent shas come from git's own log and pass the same test. `--end-of-options` is kept as a second guard; measured accepted by `diff`, `rev-parse`, `show` and `cat-file` on git 2.55, and it has existed since git 2.24.
- A path comes from the query string and is checked twice: `safeRepoPath`'s refusals answer 400, then exact membership in the task's change list answers 404. Only a listed path reaches git, after `--`, under `--literal-pathspecs`. Git tree paths cannot be absolute or hold a `..` segment, so membership alone rules out traversal; the syntactic check exists to answer bad input as bad input. Blob sizes are read by blob sha and the HEAD comparison by `ls-tree` with the path after `--`, so no path is ever spliced into a revision argument. Known limit, shared with `/api/file`: `safeRepoPath` trims and refuses a backslash, so a file whose name begins or ends with a space, or holds a backslash, is listed and cannot be opened.
- Git is run through the existing `git()` helper, which is `spawnSync` with an argument array and no shell. `--no-ext-diff` and `--no-textconv` are part of the security posture and not only of correctness: measured, a configured `diff.external` program runs in place of the patch, and a GET must not run a program the repo's config names.
- The routes are GETs under `/api/`, so the host-header check and the serve key apply to them unchanged, and no POST is added. Responses carry Reggie's own sentences, never git's stderr.
- A failed git read is reported, never flattened to empty. The three new helpers return `null` on failure where the existing ones return an empty string under `allowFailure`; measured, unrelated histories and a missing branch both exit 128.
- The editor link follows the text that is on screen: the task worktree's copy for a live task, the serving checkout's copy for a landed one, none otherwise. Rejected: always linking the serving checkout, which for a live branch opens the unchanged file at the branch's line numbers.
- An end-of-line-only change shows as pairs of deleted and added rows that look identical once the carriage return is dropped. Accepted for now and named here so nobody reads it as a parser fault.
- `TaskInfo.branchRef` is an additive field on two existing payloads. Checked: test files are excluded from `tsconfig.json`, and the one hand-built `TaskInfo` literal in `src/workspace.test.ts` already omits seven required fields, so nothing else needs to change for the typecheck.
- The brief's front matter says `risk: low`. The front matter above carries whatever `reggie plan risk` computes from the file list; the contract document's path matches the `api` pattern, so the computed class is the one a reviewer sees, as on the previous task.
- New source, test and note files move the counts in the generated block, so `CLAUDE.md` and `AGENTS.md` are refreshed last, on a clean tree, after `npm run build`, because the installed `reggie` refuses to run behind its source.

## Out of scope
- The change story as a story scope, and the changed lens on the map. Both will read these routes; neither is built here.
- Uncommitted edits in a task worktree, a status route, a freshness strip. Committed refs only.
- A new page, a standalone diff view, or a code pane on the task page.
- Comments on hunks, approve or needs-work from the reader, or anything recorded against a diff row. Select-to-note writes the same file note it writes today.
- A `reggie diff` verb and an MCP tool.
- Expanding a gap row in place, side-by-side view, word-level highlighting inside a line, syntax colouring, and next-change and previous-change keys.
- Submodule entries. They were not measured; they are listed with their mode and whatever rows git's patch gives, with no card of their own.
- Fixing `branchChangedFiles` and `changedFiles`, which read `--name-only` as text and so return C-quoted names and obey the user's `diff.renames`. Captured as `changed-file-helpers-trust-git-quoting-and-config`. Until it lands, a file with such a name appears in "What changed" and not in `impact.actual`.
- The history reader taking a file named with ` => ` for a rename. Captured as `history-reads-an-arrow-in-a-file-name-as-a-rename`.
- The plain file page's three 404s for a path the map never read. This task softens them in diff mode only. Captured as `a-file-page-for-a-path-the-map-never-read-is-thre`.
- The plain reader's 20,000-character cut. Captured as `the-reader-stops-at-twenty-thousand-characters`.
- Reading the diff of a done task that landed without a merge commit. The answer says why there is none; reconstructing one from trailers is attribution work.
- Giving `reader.js` or `board.js` an automated test harness. The logic that needs tests is kept out of them instead.

## Bail conditions
- If `taskLanding` cannot be reused as it stands, because a done task in this repo has a landing merge it does not find or a merge it finds is not the task's, stop: the owner's ruling on done tasks rests on that lookup, and patching it belongs to the attribution work and not here.
- If any route in this task turns out to need a revision or a path spliced into a single git argument from request input, or a shell, stop and re-plan: the security posture of this plan is that revisions are shas Reggie resolved itself and paths are list members after `--`.
- If `--literal-pathspecs` or `--end-of-options` is rejected by the git that CI runs, stop and record the version; dropping either silently would leave the measured pathspec and option holes open.
- If the count-driven parser disagrees with `git diff --numstat` on added or deleted totals for any file in the fixture or in this repo's last twelve landed merges, stop: the parser is wrong, and a reader that miscounts is worse than no reader.
- If adding `branchRef` to `TaskInfo` changes the state, reason or `changedFiles` of any task in `reggie tasks --json --all` on this repo, stop: the field is meant to be read-only plumbing.
- If drawing rows in `reader.js` cannot keep `scrollTo`, the line highlight and select-to-note intact without rewriting how the plain mode renders, ship the two routes, the task page section and the contract, leave the reader in plain mode, and capture the reader half; a broken plain reader is a worse outcome than a missing diff.
- If the unmapped-file case cannot be softened inside `renderGraphLevel` without changing what a plain file page does on a 404, stop and re-plan the host: with 39 of 64 landed files being records, a door that opens onto an error page for most rows is not shippable.
- If the 60,000-line fixture makes the suite flaky or adds more than ten seconds to it, shrink the fixture to the smallest size that still crosses two page boundaries and say so in the packet, and do not weaken the paging assertions.
