# Once a repo or area has one note there is no way to add another from the page

## Problem
A file page always offers a way to write a note about the file. `fileAddNote` at `packages/reggie/src/story.ts:1644` builds a section with id `add-note`, heading "Add a note", no paragraphs and an action carrying `form: "note"`, and `fileStory` lists it at `story.ts:1473`. Because the client renders an empty section's inline form — `emptyBlock` at `ui/story.js:808` appends `noteForm` for any `action.form === "note"` — a section that is permanently empty is permanently a form.

`repoStory` and `areaStory` have no such section. What they have is an empty-state action on a section that carries content the rest of the time: `whatSection` at `story.ts:882` and `areaReadFirst` at `story.ts:1320`. Those sections are empty only while nothing has been written, so the act of writing the first note is what takes the form away.

Measured, not inferred. A throwaway probe built four repos, each with two source files under `src/big`, and asked `repoStory` and `areaStory` what they emit:

| repo state | repo `what` | area `read-first` |
|---|---|---|
| no notes at all | empty, form | empty, form |
| one `_repo` note with a `why` entry | 1 paragraph, no form | 2 paragraphs, no form |
| `_repo` note plus the folder's own note | 1 paragraph, no form | 2 paragraphs, no form |
| only the folder's own note, no `_repo` | empty, form | 1 paragraph, no form |
| `_repo` note with a `how` entry and no `why` | empty, form | 2 paragraphs, no form |

Row two is the one that matters, because it is the state `reggie onboard` leaves every repo in. `noteChain` at `story.ts:628` starts with the `_repo` note and then walks every ancestor folder before the entity itself, so a single repo-level note fills the read-first section of every area in the repo at once. From the first minute of a repo's life under Reggie, no area page anywhere has a note form.

The second paragraph that row two prints makes it worse than silence. `areaReadFirst` pushes a gap sentence when the chain is non-empty and the folder has no note of its own, and the probe caught it verbatim: "No note is written on `src/big` itself; everything above is inherited from the repo and the folders around it." The page says in so many words that nothing is written about this folder, and offers no way to write it.

Row five is the reverse mismatch and is also live: `whatSection` counts only `why` entries, so a `_repo` note of `how` entries leaves the repo page with a form while every area page in the same repo has none.

This repo demonstrates row three. Its `_repo` note carries a `why` entry and a `how` entry, so "About this repo" is full, its form is gone, and no area page has ever shown one.

Two further facts were found while reading and change what the fix has to touch.

The client already advertises an anchor that does not exist. `explainActions` at `story.ts:2180` appends `{ label: "Add a note", route: "<route>#add-note" }` to every Spotlight, whatever the node's kind, and `ui/dev/sample-explain.json:32` is a checked-in sample of that action pointing at an **area** route. `renderSpotlight` at `ui/story.js:1135` prefers `onAddNote`, which `ui/app.js:1533` wires to `focusNoteForm()` with the fallback toast "Open a file or an area to add a note there." — a sentence that names areas, where the form has never existed.

Four exact-list assertions pin the section ids, not the two the brief names. `src/story.test.ts:226` and `:357` hold the repo and area lists, and `test/serve.test.ts:356-357` holds the same two lists again over the HTTP payload. The file, task and workspace lists in both files stay as they are.

Nothing is lost that cannot be recovered from a terminal — `reggie note add` takes any entity and the MCP tool reaches the same function — but the 2026-09-15 decisions ratify three doors for capture, and for notes the web door exists at file scope and half-exists above it. The reader who is on an area page because they are trying to understand that area is the person most likely to have something worth recording about it, and they are the one told to go elsewhere.

## Approach
Emit the always-present section at repo and area scope as well as file scope, from one scope-neutral builder, and carry the same change into the four exact-list assertions, the contract, the spec, the client's skeleton table and the two repo-scope dev samples. Nothing is built: the client renders the section the moment the payload carries it.

**1. One builder, three callers.** `fileAddNote(node)` becomes `addNoteSection(scope, entity)`, taking the scope so it can pick its empty text and the note entity so it can spell the terminal hint. `repoStory` calls it with `"_repo"`, `areaStory` with the folder entity, `fileStory` with `node.id`. The rejected alternative is three near-identical section builders, which is how `testedClause` came to have three hand-built copies that drifted — the lesson `false-tests-sentence` landed on 2026-09-15 and the reason this one has a single formatter.

**2. The area's note entity is written once.** `areaReadFirst` already computes `dirPath === "." ? "_repo" : \`${dirPath}/\`` at `story.ts:1320`, and the new section needs the identical expression. It is lifted into one module-local helper that both call. The `.` branch is not hypothetical: the probe confirms `areaStory(ctx, ".")` returns a story with `id: "."` titled with the repo name, so the repo root is reachable as an area page and its hint must read `reggie note add _repo`.

**3. Position: last, at all three scopes.** Repo becomes `needs-you, what, made-of, starts, talks, flight, recent, gaps, run, add-note`; area becomes `read-first, inside, uses, used-by, tests, people, tasks, recent, add-note`; file is unchanged with `add-note` already last. One rule for three scopes is the only arrangement a reader and a test both learn once, and it holds the lens arrangement for free: `areaStory` and `fileStory` push `gaps` after the base list when `lens=knowledge`, so `gaps` stays last at both and the assertion at `story.test.ts:363` passes untouched. The repo has no lens push, so nothing constrains it there.

**4. Empty text becomes one sentence per scope.** `EMPTY_TEXT.fileAddNote` is replaced by `addNoteRepo`, `addNoteArea` and `addNoteFile`. The file string is kept byte-for-byte — "Write what the next person should know about this file." — and the other two differ from it by one noun: "…about this repo." and "…about this area." The noun "area" rather than "folder" matches `EMPTY_TEXT.notes`, which is the other empty state on the same page and is quoted from spec §4.

**5. The terminal hint says `--type why` at all three scopes.** This is a correction as well as an extension. `noteForm` at `ui/story.js:706` defaults its type select to `opts.type ?? "why"` and `emptyBlock` passes no opts, so the rendered form posts `why` whatever the hint says — while `fileAddNote` today hints `--type how`. The hint's only job is to be the terminal equivalent of the button beside it, and at file scope it is not. The three other note actions on these pages (`whatSection`, `areaReadFirst`, `fileReadFirst`) already hint `--type why`, so `why` is the repo's existing web default and the file add-note hint is the single outlier. On the repo page this is the consequence the brief flags: a `why` entry lands under "About this repo", where the reader was just reading, rather than as a card under "How to run it". `story.test.ts:458` asserts only `toContain("reggie note add src/big/a02.ts")` and does not pin the type, so the correction breaks nothing.

**6. Two client edits, both of them lists that duplicate the payload.** `HEADINGS.repo` and `HEADINGS.area` in `ui/story.js:52` each gain `["add-note", "Add a note"]` last, because `sectionHeadingsFor` drives `renderSkeleton` and leaving them means every repo and area page reflows by one section as the payload lands. `ui/app.js:1533`'s toast is reworded to name all three scopes. The rendering itself — `emptyBlock`, `noteForm`, `noteEntityFor`, `focusNoteForm` — is not touched, which is the brief's "Not this" and is also why the change is small.

**7. The three written records of the payload's shape.** `docs/ui-api-contract.md:127` lists section ids by scope in one line and is what a client author reads instead of the code. `docs/ui-spec.md` needs three edits: an `add-note` row in the §2 repo table, **Add a note** named in the §3 Level 2 area walkthrough, and a §4 row distinguishing the always-present section from the "Notes (any chain)" empty state, which stays exactly as it is. `ui/dev/sample-story.json` and `ui/dev/sample-story-empty.json` are both repo scope and both list section ids; there is no area-scope sample to update.

**8. The empty states are left alone, and a page may carry two forms.** `sample-story-empty.json` is the harness's "repo, every empty state (forms)" fixture and becomes the place a reviewer can see the two-form case with their own eyes. The duplication is accepted rather than designed around; the reasoning is in Assumptions, and it rests on the measurement that both forms on a page already write to the same entity.

## Assumptions
The owner is asleep and unreachable. The brief carries one `Answered by jacobpress on 2026-09-15` line and it is binding and honoured below. Every other open question is answered here, unattended, on 2026-09-15, with the evidence each answer rests on.

- **Only the repo, area and file scopes get the section.** Binding, answered by jacobpress on 2026-09-15: no, repo, area and file only, per one repo at a time; the other pages get it when someone captures the ask. So `workspaceStory`, `taskStory`, the services story and the flow story are untouched, and criterion 5 pins their lists so the change cannot leak into them. The inconsistency it leaves is real and named: `noteEntityFor` at `ui/story.js:251` maps a workspace story to `_repo`, so the workspace page could carry the form and deliberately does not.
- **The section goes last at every scope.** The file page already puts it last, and a reader who learns once that the way to write a note is at the foot of the page does not have to learn it again per scope. Placing it beside "About this repo" would put an always-empty form between the blurb and the inventory, above the fold on the page whose job is to answer what the repo is. Placing it after "Read these first" on an area page would displace "What is in here", which is the section the reader opened the page for. Last also costs nothing on the repo page, where `run` renders as a `<details>` collapsed by default (`commandsBlock`, `ui/story.js:840`), so the new section is never pushed below a long block.
- **The knowledge lens keeps `gaps` last, and the gaps push is not touched.** `areaStory` and `fileStory` both append `gaps` after the base list, so putting the new section last in the base list leaves `gaps` last under the lens by construction, and the existing assertion at `story.test.ts:363` passes unedited. Reversing the arrangement — pushing `gaps` before the form — would put a diagnostic that names what is missing after the control that fixes it, which is the wrong reading order, and it would mean editing a passing assertion for aesthetics inside a task whose whole risk is churn in exact-list tests.
- **The terminal hint says `--type why` at all three scopes, which changes the file hint from `how`.** The rendered form's type select always defaults to `why`: `noteForm` at `ui/story.js:706` reads `opts.type ?? "why"` and `emptyBlock` at `ui/story.js:815` calls it with no opts. So the file page's hint and its own button already disagree, and copying that disagreement to two more scopes would triple it. The other three note actions on these pages all hint `--type why`. On the repo page the choice is not cosmetic, exactly as the brief says: `whatSection` renders only `why` entries and `runSection` renders every other type, so `why` puts the reader's note under the prose they were just reading. The alternative, teaching `emptyBlock` to pass a per-scope type through to the select, is a client change and a contract change — `StorySection.empty.action` has no `type` field at `docs/ui-api-contract.md:117` — and it is captured rather than done.
- **The empty text is three sentences, one per scope, differing by one noun.** A single scope-neutral sentence would have to end "about this.", which is the weakest sentence available and throws away the section's one chance to say what is being written about. Three freely written sentences would be three registers to keep in step. Parallel sentences are the answer to both: "Write what the next person should know about this repo." / "…about this area." / "…about this file." The file sentence stays byte-identical so nothing that quotes it moves. The noun "area" rather than "folder" matches `EMPTY_TEXT.notes`, the other empty state on the same page, which spec §4 says must not be reworded.
- **The heading stays "Add a note" at all three scopes.** The section id is already scope-neutral and already published as an anchor: `explainActions` at `story.ts:2180` emits `#add-note` on every Spotlight route regardless of kind, and `ui/dev/sample-explain.json:32` is a checked-in example of it on an area route. The empty text under the heading names the target and the form itself prints the entity it will write to (`ui/story.js:721`), so the heading would be the third and least useful place to name it. Three pages headed identically is the point: it is the same control. Varying it by scope would also mean a second literal per scope in `HEADINGS` and in `headingFor`.
- **A page may carry two note forms, and that is accepted.** It is not a new class of behaviour: a file page in a repo with no notes at all already renders two, the `read-first` empty state and `add-note`, and has since the section was introduced. It is also harmless, because both forms on a page write to the same place — `noteForm` takes its entity from `noteEntityFor(story)`, which is derived from the story's scope and id and not from the section, and `emptyBlock` passes no override. The two forms therefore differ only in the sentence above them and the hint beside them, which is why `focusNoteForm` picking the first `.form--note` in the document cannot pick a wrong target. The duplication is also self-limiting: it exists only while nothing has been written on the page, and the first note ends it. The alternative — dropping the form from the empty states above file scope — is what the brief's "Not this" rules out, and it would leave "About this repo" with an empty state carrying no action at all.
- **The client's skeleton heading rows ride along.** `sectionHeadingsFor` at `ui/story.js:1027` reads the same `HEADINGS` table and drives `renderSkeleton`, which is what a reader sees while the story loads. Leaving the two rows alone means every repo and area page visibly reflows by one section as the payload lands — a defect this change would introduce, not one it would inherit. It is two lines in a table that is already hand-kept in step with the payload for every other section, and the brief holds this open as a question rather than excluding it; the exclusion is about `emptyBlock` and `noteEntityFor`, which stay untouched.
- **The Spotlight's fallback toast rides along.** "Open a file or an area to add a note there." is false today, because an area page in any set-up repo has no form, and it would be differently false afterwards, because it would still be silent about the repo page. It is one string in the same commit as the thing that makes it true. The reader drawer's own fallback at `ui/app.js:1431`, "There is no note form on this page.", is already scope-neutral and is left alone.
- **The Spotlight can focus a form pointed at a different entity than the node it is describing, and that is left as it is.** Tapping an area node on the repo map pins that area's Spotlight; its "Add a note" button calls `focusNoteForm()`, which finds a form on the current page, and after this change the repo page always has one, pointed at `_repo`. The same mis-targeting already exists at file scope today. It is mitigated in place: the form prints "on `<entity>`" above the textarea, so the reader can see where the note will land before submitting. Making the Spotlight's button carry its node's entity into the form is a real improvement and is captured, not done here, because it needs a `type`-and-`entity` channel on the action that the contract does not have.
- **`test/serve.test.ts` is in scope even though the brief does not name it.** It holds the same repo and area exact lists again at `:356-357`, over the HTTP payload rather than the function return. Four assertions change, not two. Leaving it out would turn a planned edit into a surprise red test during the build.
- **The `ui/dev` samples ride along, and there is no area sample to add.** `sample-story.json` and `sample-story-empty.json` are both repo scope and both list section ids; `sample-story-file.json` already carries `add-note`; there is no area-scope sample in `ui/dev`. `sample-story-empty.json` is the harness's "every empty state (forms)" fixture, so it is where the two-form case can be seen rather than argued about, which is why criterion 21 asks for a screenshot of it.
- **The `label` on the action stays `"Add note"`, unchanged and unaligned with the other three actions' `"Add a note"`.** `emptyBlock` never renders the label for an action carrying a form: it appends the form, and the hint line then reads "Or from a terminal: " because `action.form` is set. Changing the label would be a diff with no observable effect, and this task adds two call sites rather than reopening one.
- **`reggie note add` accepts every entity the three hints spell.** `resolveNoteTarget` at `src/notes.ts:48` maps `_repo`, `.` and `./` to the repo note, treats a trailing slash as a directory, and otherwise resolves against the working tree. `POST /api/note` at `src/serve.ts:2122` passes the entity straight to `addNote` and scope-gates nothing, so a repo or area entity posted from the page lands exactly where `reggie note add` would have put it. `serve.ts` is read here and is not edited.
- **The evidence comes from throwaway `tsx` probes run from the scratchpad, not from files added to the repo.** `vitest.config.ts` includes only `src/**` and `test/**`, so the `sectionHeadingsFor` check in criterion 16 is a node script against `ui/story.js` rather than a test, in the same shape `graph-coverage-published` used for `footerFor`.
- **`TZ=UTC` is set for the suite deliberately.** `src/tasks.test.ts`'s "assembles plan, packet, claim, journal, and impact as a task moves" fails in local evening time because `ageInDays` parses a bare `YYYY-MM-DD` as midnight UTC against a locally written date. It is unrelated to this task and already captured. Under `TZ=UTC` on this worktree at `dd613ed` the suite is green: 31 files, 653 passed, 1 skipped, exit 0. That is the baseline every criterion here is measured against.
- **Four findings were captured during this pass rather than fixed**: the note form's type select ignoring the action's intended type, so the hint and the button can disagree; the Spotlight's "Add a note" focusing whatever form is on the page rather than one for the node it describes; the `#add-note` fragment in `explainActions` being emitted for task and entity nodes that have no such section and no note form; and the repo root reached as an area page rendering "on `./`" in the form while its hint says `_repo`.

## Out of scope
- Any change to how the client renders the form. `emptyBlock`, `noteForm`, `noteEntityFor` and `focusNoteForm` already handle the section and already map a repo story and an area story to the right entity; criterion 18 pins them unchanged. The two client edits here are the skeleton heading rows and one toast string, both of which are lists or sentences that duplicate the payload.
- Rescuing the empty states on "About this repo" and "Read these first". They keep offering the form when they are empty. Making an area's read-first count only its own notes so it goes empty again is a different change with a different cost, and it would make the section lie about what a reader should read first.
- Removing the form from the empty states above file scope to avoid two forms on a page. Ruled out by the brief and answered in Assumptions on the evidence that both forms write to the same entity.
- Giving the workspace, services, flow and task pages the section, and giving any entity-kind note target a page-level form. Excluded by the binding answer of 2026-09-15.
- Teaching the action a note type the select will honour, or an entity the Spotlight can hand it. Both need a field the contract's `empty.action` does not have; both are captured.
- How notes are stored, resolved, typed or aged. The note entity spellings, the note types, confidence and the staleness rules are all read here and none of them changes. `src/notes.ts` and `src/serve.ts` are read-only in this task.
- Editing, deleting, retiring or listing existing notes from the page, and any notes index. `notes-have-no-way-to-retire-an-entry` is its own item. This is one more way in for a new note and nothing else.
- The reader drawer's line-range prefill. It is a file-scope surface with its own trigger and its own prefill text; it reaches the same form and is unaffected by the form appearing elsewhere.
- The idea action that the 2026-09-15 decisions put on every page, and `go-deeper-on-own-page`. They will sit near this on the same pages and are separate work.
- The knowledge lens, the gaps sections and the stale rules. They are the reason the missing form is noticeable on area pages and they are not edited here beyond keeping `gaps` last.
- The pre-existing `src/tasks.test.ts` timezone failure, which is captured as its own intake item and is neither chased nor fixed here.
- Re-examining the made-of coverage paragraph and the tested clause that `graph-coverage-published` and `false-tests-sentence` landed hours ago. They share `story.ts` and touch its prose; this touches its section lists.

## Bail conditions
- Adding the section to `areaStory` moves any assertion other than the two exact-array lists and the section-count arithmetic that follows from them, which would mean a section list is load-bearing somewhere this plan did not find and the placement question has to go back to the owner.
- `gaps` stops being the last section under `lens=knowledge` at area or file scope, which would mean the lens push is not the simple append this plan reads it as and the lens ordering needs its own item.
- A repo or area page is found where the two forms do not resolve to the same note entity, which would break the reasoning that makes the duplication harmless and would force the choice between dropping the empty-state forms and changing `focusNoteForm`.
- The repo root reached as an area page turns out to be unreachable from the client's router, which would mean the `.` branch in the entity helper is dead code and the helper should not exist.
- `renderSkeleton` turns out to be fed headings from somewhere other than `sectionHeadingsFor` for the repo or area scope, which would mean the reflow this plan prevents was never possible and the two `HEADINGS` rows are churn.
- The repo page with the section last is measured to push "How to run it" or the new section below a scroll on a phone-width layout, which would mean placement is a layout question rather than a reading-order one and belongs with the layout-modes work.
- Changing the file hint from `--type how` to `--type why` turns any test red, or is found to be quoted as the specification anywhere outside `docs/ui-spec.md`, which would mean the hint is a published string and the correction needs its own item.
