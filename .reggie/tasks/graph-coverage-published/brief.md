# The map never says what it skipped; unresolved imports and skipped languages are computed and discarded

## Problem
The map draws a picture of a repo and never says which part of the repo the picture is of. `buildGraph` keeps only the files whose extension sits in `CODE_EXT` — TypeScript, JavaScript and Rust — and everything else is dropped before a single node exists. A Go service, a Swift app, a Python script, a Kotlin module: no file node, no import edge, no area, no note attachment, no history roll-up. The page that results is not marked as partial anywhere. It renders exactly as it would for a repo Reggie read from end to end, so a folder with forty Go files and a folder that is genuinely empty are drawn the same way, which is to say not at all. The reader Reggie exists to serve is the one who has not read the code; they are precisely the reader who cannot tell the difference, and the page gives them no reason to suspect there is one.

The same is true of the imports inside the languages it does read. `buildGraph` counts every relative import specifier that resolved to no file and keeps the total as `unresolved`. The number is honest and it is already on `RepoGraph`. `flatGraph` copies it, together with `languages`, onto the no-parameter `GET /api/graph` payload — and that payload is the compatibility shape, the one the client never asks for. `app.js` fetches `/api/graph?level=container`, `/api/graph?level=dir`, `/api/impact` and `/api/workspace`; nothing in the UI requests `/api/graph` bare, and nothing anywhere in `ui/` mentions `unresolved`. So both numbers are computed correctly, serialized faithfully, and read by nobody. The work is already done and thrown away at the last step.

What the map does read is the counts block of the level payloads, `ViewCounts`: `totalCodeFiles`, `shown`, `folded`, `hiddenTests`, and the per-hop `up` and `down` on impact. It is built at three sites — the container view, the directory view and the impact view — and `footerFor` in `map.js` turns it into the footer line for each level. That block is the channel through which the map learns anything numeric about itself, and every number in it describes how much of the graph is on screen. None of it describes how much of the repo is in the graph. The distinction is the whole item: the footer can already say "Showing 40 of 63 files", and that is a statement about folding, not about reading.

`totalCodeFiles` is part of the trap rather than the way out of it. It is the length of the list after the `CODE_EXT` filter, so the total the footer compares against has already had the skipped languages removed from it. A reader who sees "Showing 40 of 63 files" in a repo of four hundred files is being told a true thing in a form that invites a false conclusion, and the number that would correct it — the count of files the graph never looked at, broken down by language — is the one number the payload does not carry.

The story's made-of section has the same shape of problem in prose. It writes one paragraph per Level-1 area, ordered by source count, built entirely from the container view; it is the page's literal answer to what the repo is made of, and it is an inventory of the survivors. Nothing has to be computed to fix it: `collectFacts` already walks every tracked file against a much broader table than `CODE_EXT` and returns a per-language count that includes Go, Swift, Kotlin, Java, Python, Ruby, C#, C, C++ and Objective-C. Both halves of an honest sentence — what the repo is made of, and what the graph read of it — are already in the same process, and one of them is thrown away before it reaches the page.

So the item is three publications of two numbers that already exist: a skipped-by-language count and the unresolved count added to the counts block of the level payloads, one sentence in the made-of section built from the same two numbers, and the unresolved count in the map footer. The flat `/api/graph` is not the route to fix; it is the evidence that publishing a number somewhere is not the same as publishing it where the reader is.

It is an honesty item before it is a feature. The claim on Reggie's front page is that an owner can trust what it says about a repo they have not read. A map that silently omits three quarters of a polyglot repo does not fail that claim loudly; it fails it invisibly, which is worse, because there is no moment at which the reader is given the chance to discount what they are looking at. The rule the work has to satisfy is simply that the map says how much of the repo it read.

## Why now
The decision of 2026-09-15 to defer more languages is what makes this urgent rather than moot. If the plan were to read Go and Swift next month, a disclaimer would be a stopgap. The plan is the opposite: Reggie is built against this repo and `personal_website` first, both already fully parsed, and more languages come only once it is in good shape. That means the gap between what Reggie reads and what a repo contains is a standing condition for as long as anyone can see, and the only mitigation available is to say so on the page. Deferring the languages and deferring the disclaimer together is the combination that produces a confidently wrong map.

It also becomes more expensive to add later. Every surface that grows on top of the graph — the lenses, the treemap, the area pages, the narration and the episodes — inherits the silent partiality of the payload it reads, and each one is another place a disclaimer has to be retrofitted. Adding the two numbers to the counts block now means the surfaces built after it can read a payload that already knows what it skipped.

Against that, the change is nearly free. The unresolved count exists. The every-language count exists in facts. The counts block is already threaded to the client and already rendered by the footer. Nothing has to be parsed, resolved or inferred; the work is choosing the wording and the placement, which is what the small-items stretch after the loop plumbing is for.

The ordering constraint is the last reason to shape it now rather than later: `false-tests-sentence` edits the same made-of sentence and the same `ui/dev` fixtures, and it has to land first. Shaping both in the same pass is what keeps the second one from being written against a paragraph that is about to change under it.

## Suspected area
- `packages/reggie/src/views.ts` — `ViewCounts` and the three places it is built: the container view, the directory view, and the impact view where it is assembled as a named value before the `up` and `down` arrays are attached. The new fields belong here because this is the block the map actually reads.
- `packages/reggie/src/graph.ts` — `CODE_EXT` is the filter that decides what is skipped and `unresolved` is accumulated in the edge pass; `RepoGraph` already carries `unresolved` and `languages` for the view builders to lift. Whatever shape the skipped-by-language breakdown takes probably has to be produced here, where the filtered list and the full list are both still in hand.
- `packages/reggie/src/facts.ts` — `LANGUAGE_BY_EXT` and `collectFacts` are the every-language count the skipped number has to be taken against, and `RepoFacts.totalFiles` is the denominator a coverage claim would use. Read first to decide whether the graph should call it or recount.
- `packages/reggie/src/story.ts` — `madeOfSection` builds the paragraphs the new sentence joins, from the container view. It is also the file `false-tests-sentence` edits, in the same clause.
- `packages/reggie/ui/map.js` — `footerFor` composes the footer per level with the `plural` helper, and already has separate branches for container, dir, impact and workspace. The unresolved count has to fit those branches without crowding the counts that are already there.
- `packages/reggie/src/serve.ts` — `graphRoute` and `impactRoute` are how the level payloads reach the client, and `flatGraph` is the compatibility payload behind the bare `/api/graph`. Mostly read-only here: the point is to confirm that nothing else depends on the flat shape before deciding what to do with it.
- `packages/reggie/ui/dev/sample-container.json`, `sample-dir.json`, `sample-dir-tests.json`, `sample-impact.json`, `sample-story.json` and `gen-samples.mjs` — the dev harnesses render from these, so a counts block that gains fields leaves the harness showing the old footer until the samples carry them.
- `packages/reggie/docs/ui-spec.md` — the made-of row quotes the paragraph as its own specification and the layout section quotes the footer line as its example, so both say the pre-change wording until they are edited with the code.
- `packages/reggie/ui/DOM-CONTRACT.md` — the `map-footer` row describes the footer's content in the same example form.
- `packages/reggie/src/views.test.ts`, `graph.test.ts`, `story.test.ts` — `graph.test.ts` already asserts `unresolved` on both the full and the flat graph, which is the fixture to extend; nothing asserts that the number reaches a view or a page, which is why it could be discarded unnoticed.
- `packages/reggie/ui/dev/make-fixture-repo.ts` — the fixture repo is where a skipped language has to exist for any of this to be testable; if it is all TypeScript today, the skipped count is zero in every test and the new sentence never renders under test.

## Open questions
- Is the skipped count a single number, a per-language breakdown, or both? The intake line says "a skipped-by-language count", which reads as a breakdown, but a footer has room for one number and a made-of sentence has room for two or three named languages. The decisions of 2026-09-15 do not settle the shape of the field, and the shape decides whether the footer can be built from the same value the sentence uses.
- What is the denominator — every tracked file, or every file with a recognised language? `collectFacts` counts only files whose extension is in its table, so Markdown, YAML and images are outside both the graph and the language census. A skipped count taken against all tracked files says something much larger and much less useful than one taken against recognised code.
- The unresolved count is repo-wide, but the footer is per-view. Does the container, directory and impact footer each repeat the same repo-wide number, or does the number get scoped to the files drawn in that view? A dir footer that reports a repo-wide total is reporting something that is not about the directory the reader is looking at, and scoping it means counting unresolved specifiers per file, which the graph does not do today.
- Does `unresolved` count occurrences or distinct specifiers? It increments once per import reference, so one bad path imported from twelve files counts twelve times. Whichever the footer publishes, the wording has to match, and "12 unresolved imports" and "1 unresolved import used in 12 files" are different claims about how broken the graph is.
- Should the footer say the unresolved count at all when it is zero, or vanish? A footer that says nothing is indistinguishable from a footer that was never given the number, which is the exact failure this item exists to end; a footer that says "0 unresolved" on every healthy repo is noise in the place the reader looks most often.
- Where in the footer line does it go, and what does it displace? The container branch reads "7 areas · 12 edges · 49 tests hidden" and the dir branch already prepends the folding sentence. The footer is a single line in a floating card at the bottom right of the map, and the plan needs a rule for what gets dropped when the line will not fit rather than discovering it at three widths.
- Does the made-of sentence sit at the top of the section or the bottom? At the top it frames every area paragraph that follows as a partial account; at the bottom it reads as a footnote. The decisions do not say, and it changes how strongly the page disclaims itself.
  > Answered by jacobpress on 2026-09-15: First paragraph of the section, so the reader can discount the inventory before reading it.
- Does the sentence name the languages it skipped, or only count them? Naming Go and Swift is far more useful to the reader and far more likely to be wrong in a long tail of one-file languages; counting is safe and nearly useless.
- What does the sentence say when nothing was skipped and nothing is unresolved, as is true of this repo today? Saying "Reggie read all of it" is a positive claim worth making and is also the sentence most likely to be quoted back when it turns out to be false; saying nothing returns the page to silence in the common case and leaves the feature untested on the repo it is developed against.
  > Answered by jacobpress on 2026-09-15: Make the positive claim: Reggie read all N code files and followed every import. The honesty rule cuts both ways and it keeps the feature exercised on this repo.
- Does this also belong on the workspace payload? `footerFor` has a workspace branch and `workspace.ts` has its own per-language counting, but the one-repo-at-a-time decision of 2026-09-15 pushes cross-repo work out. Whether the workspace footer stays silent while the repo footer starts disclaiming is a consistency question the decisions do not answer.
- What happens to the flat `/api/graph` payload's `unresolved` and `languages` once the counts block carries them? Leaving two sources of the same numbers is how they drift apart; removing them changes a route that is documented as a compatibility shape and may have readers outside this repo.
- Does the file the reader opens say anything? A Go file exists in the tree and has no node in the graph; if the reader navigates to it, the page it gets is built from a graph that has never heard of it. The item as captured covers the map and the story, and whether the file page needs the same disclaimer is unsettled.
- Is "unresolved" the word the footer should use? It is precise and it is jargon. The reader being addressed is the one who has not read the code, and an import Reggie could not follow may be better described than named.
- Does the fixture repo need a skipped language added to it, and does adding one perturb the other tests that count files in it? Without one, every assertion about the new numbers is an assertion about zero.

## Not this
- `false-tests-sentence`. It edits the same made-of paragraph, at the clause that prints a file count under a tests label, and it touches the same `ui/dev` samples and the same spec row. It lands first; this one is written against the paragraph it leaves behind. Merging them would put a correction and a disclaimer about two different kinds of wrongness into one change, and landing them in the wrong order publishes a coverage disclaimer next to a coverage lie.
- Reading new languages. Adding Go, Swift, Kotlin or Python to `CODE_EXT` and giving them resolvers is M-Lang, deferred by the decision of 2026-09-15. This item is the honest description of the gap, and it must not narrow the gap even a little, or it becomes that work wearing a smaller name.
- Making the unresolved imports resolve. Path aliases from tsconfig, package self-references, extensionless directory imports and index resolution are all reasons a relative specifier can miss, and improving the resolver would lower the number this item publishes. Publishing the number is the task; reducing it is a separate one that should be argued on its own evidence.
- Coverage in the testing sense. "How much of the repo the map read" and "how much of the code is tested" are two different meanings of coverage that are about to appear in the same paragraph, and nothing here should touch the test counts, the tests lens, or the Tests section.
- The workspace map and cross-repo discovery, held back by the one-repo-at-a-time decision unless the question above settles otherwise.
- Redesigning the footer, the toolbar or the legend. The footer gains one number inside the composition that already exists; the floating-card layout and its behaviour at narrow widths are their own work.
- Removing or reshaping the flat `/api/graph` route. What its duplicated fields should become is an open question above; treating the route itself as a cleanup target is a separate item.
- The treemap tab, the lenses, and anything that colours nodes by coverage. This is two numbers and two sentences, not a new view.
