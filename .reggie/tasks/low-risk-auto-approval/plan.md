# Low-risk auto-approval, first slice — checks recorded as data, the evidence gate, discovered issues captured on approval, one landing at a time, and the policy's verdict as a report that merges nothing

## Problem
The 2026-09-15 decision is that in solo mode plans of every risk class and low-risk completions pass by policy, and it names four preconditions: a packet citing evidence that does not exist never passes, checks are recorded as data, Reggie owns the merge, and a packet's discovered issues are captured automatically. This task lets software merge code with no person reading it, so this plan is written as a safety case. The brief describes older code; what is true today was measured on 2026-09-18, in throwaway repositories built with `reggie onboard` under the session scratchpad and, read-only, on this repository's fifteen landed loop tasks. Every measurement below was taken in a throwaway repository or is a read of this one.

The owner's answers in the brief are binding and reverse part of its Problem text: in solo mode plans of every class pass, so the brief's paragraph that holds medium and high plans at groomed is not planned; completions pass at low only; a completion passes only when every plan criterion has a passing check and no check of any kind fails, and a packet with no checks never passes; the policy is evaluated inside `reggie packet` plus a standalone verb by hand; one class per packet kind; team mode is deferred.

What was measured:

- **M1, nothing checks a packet today.** A packet exactly as `reggie packet` scaffolds it, nothing ticked, every evidence line still the placeholder, no evidence folder, was approved and merged by `reggie decide approved` without a word. A ticked packet citing two files that exist nowhere on the branch merged the same way (M2). The only protection seen is accidental: while the evidence sits untracked in the task worktree, `landTask` refuses because the worktree is dirty; once the files are gone, or the claim was made in place, nothing notices.
- **M3, the merge runs only where the base branch is checked out.** `reggie decide approved` typed inside the task worktree refuses with "this checkout is on task/beta, not main". Driven with `-C` at the integration checkout while standing in the worktree it merges, releases, and deletes the directory the shell is standing in: afterwards `git status` answers "Unable to read current working directory" and `reggie tasks` answers `ENOENT … uv_cwd`. The Reggie process itself survives and exits 0, because every git call it makes names its directory. An in-place claim has no checkout on the base branch at all and is refused the same way. From inside a task worktree, `git worktree list --porcelain` names every checkout and its branch, and a Reggie worktree is always `<integration checkout>/.worktree/<slug>`.
- **M4, a dirty integration checkout refuses, and the page lies about why.** A modified `README.md`, or one uncommitted `reggie capture` in the integration checkout, refuses the landing with the file named. In the web client `friendlyError` turns every 409 from the decide route into "No completion packet exists for this task yet", so the one actionable sentence is discarded (already captured as `approving-from-the-web-board-fails-whenever-the`).
- **M5, one capture on each side is a merge conflict.** With one intake line committed on the base and one captured on the branch, the landing aborts on `.reggie/intake.md`, both branches untouched. Thirteen of the fifteen landed branches touched the intake file. `git merge-tree --write-tree --name-only` (git 2.55 here) reports the same conflict with exit 1, and exit 0 for a clean pair, without touching any checkout.
- **M6 and M7, a branch can rewrite what it is judged by.** A branch that set its own plan from `risk: high` to `risk: low` and deleted a criterion still passes `reggie plan lint`, and `reggie packet` run in its worktree wrote `risk: low` and one criterion into the packet. `reggie` run inside the worktree obeys the worktree's copy of `.reggie/config.yaml`: after the branch wrote `mode: team` and an invented `policy` block, `reggie people` said team there and solo in the integration checkout. A hand approval then merged all of it, and the repository was in team mode. Of the fifteen landed branches, two edited their own plan (one added three files to the list, one reworded two criteria and added a third, with the owner's agreement at the time) and one changed the config; none touched another task's folder, the people file, `.mcp.json`, `.gitattributes` or `.claude/`.
- **M8 and M9, criteria.** A plan with no `- [ ]` line fails lint, and the scaffold's stand-in bullet is not read as a criterion, so "every criterion has a passing check" would be true of nothing. Two identical criteria pass lint. Markdown, pipes, quotes and `[[…]]` are kept verbatim. A criterion that wraps onto an indented second line is cut to its first line by `parsePlan`.
- **Risk from the plan against risk from the branch.** On the fifteen landed tasks the plan was on the base at merge time every time and its front-matter class always equalled the class recomputed from its own file list. Nine of fifteen branches changed a code file the plan never named, and all fifteen changed some file outside their own task folder that the plan never named (notes and the intake file, mostly). Recomputed from every file the branch changed outside its own task folder and the journal, the class rose once: `task-attribution-by-merge`, low to medium, because eighteen files is more than twelve.
- **Citations.** Today's reader of `evidence:` lines drops any piece that holds a space, so it links evidence for 220 of the 306 criteria in the fifteen landed packets, and in five of them for at most two (2 of 28, 1 of 19, 1 of 15, 0 of 8, 1 of 15); that is the captured item `a-packet-s-evidence-line-with-prose-after-the-path-links-not`. It also returns `../../../etc/passwd` and `/etc/hosts` as references, verbatim. A prototype rule, the leading path of each comma-separated piece on `evidence:` lines and `## Evidence` bullets, kept only when it names the task's own evidence folder, gave every one of the 306 criteria at least one reference and found 281 distinct citations in the fifteen packets; all 281 exist on the branch tip that was merged, none is a symlink, a folder or a path in a subfolder, and exactly one is an empty file, `board-diff.txt` of `intake-line-leaves-at-triage`, an honest empty diff the owner checked by hand.
- **Discovered issues.** Fifty bullets in fifteen packets: six run over more than one line, two say none, forty-three name a slug Reggie knows (in backticks, or after "captured as" or "captured:"), and five would be captured afresh, two of which name slugs that have since been retired. None was matched by slugifying its text.
- **M10, two landings at once corrupt the integration checkout.** Two `reggie decide approved` calls started together, four rounds: twice one merged and the other failed on git's index lock; once both failed and nothing merged; once both failed, no merge commit existed, the checkout was left holding the staged half of a merge whose `MERGE_HEAD` was gone, and the board counted a packet as approved that no merge had landed. Replayed step by step with git: when B's `git merge` fails because A's merge is in progress, `landTask` runs `git merge --abort`, which aborts A's merge, restores A's files and removes A's packet from disk. Rare while a person types each approval; routine once sessions land themselves.
- **M11 to M13, smaller traps.** Approving an already landed task writes a fresh verdict commit every time. A packet on the branch that already says `approved` reads as awaiting decision and one that says `needs-work` is merged by an approval without remark. `reggie decide <slug> needs-work` typed in the integration checkout answers "No packet" although the packet sits on the task branch. `reggie packet` typed in the integration checkout scaffolds a second, empty packet there as an untracked file, which then blocks the landing. `reggie onboard` does not ignore `.worktree/`, so `git add -A` in a freshly onboarded integration checkout records the task worktree as an embedded repository.
- **Baseline.** `TZ=UTC npx vitest run` in `packages/reggie`: 37 files, 1052 passed, 1 skipped.

## Approach
**The task is split, and this plan is the first slice.** The first slice makes the four preconditions true and produces the policy's verdict as a read-only report; nothing lands without a person. The second slice acts on the verdict. The line is drawn there for three reasons. A gate and records with no automatic merge is safe to ship alone, and an automatic merge without the gate is not. The owner's own pattern on 2026-09-15 for anything a machine will do unattended was a verb first and the automation once it is trusted; here the report is that verb, and every task built between the two slices shows on its page what the policy would have said, so the first automatic landing happens after the gate has been watched refusing the right things. And the whole task is about seventy-five criteria, half again the largest plan this repository has built in one go. The second slice is captured as its own item with every design question below already settled, so its plan re-measures nothing.

**What is trusted from which commit.** The evaluation is a pure function of two commits, each resolved once to a full id through `resolveCommit` and never named again: the tip of the integration branch and the tip of `task/<slug>`. It reads no working tree.
- From the base commit: `.reggie/config.yaml` (the mode, the `policy` block, the risk rules) and the task's `plan.md` (the criteria, the `risk` line, the file list). A plan that is not committed on the base is a refusal, because there is then no copy the branch could not have edited; so is a plan that fails the contract, and so is a plan with no criteria, said in words rather than passing vacuously.
- From the branch tip: `packet.md`, `checks.jsonl`, the evidence files and the list of changed files. These are the session's claims; the evaluation believes none of them further than it can verify.
- The base branch's name comes from the integration checkout's config on disk, never from a task worktree's. The integration checkout is found by structure, not by config: a Reggie worktree is `<X>/.worktree/<slug>`, so `X` is its parent, confirmed by `git worktree list --porcelain` naming `X` with a branch that is not a task or plan branch. In `X` itself the root is `X`. A name that begins with a dash is refused before it reaches git.
- A branch that changes a file Reggie or the next session obeys is refused whatever else holds, because reading the policy from the base protects this merge and not the next one: its own `plan.md`, `.reggie/config.yaml`, `.reggie/people.yaml`, any path under another task's folder, `.mcp.json`, `.gitattributes`, and anything under `.claude/`. A person decides those. Measured, that would have sent three of the fifteen landed tasks to a person, each rightly.

**The risk class.** Effective class is the highest of three, all under the base commit's rules: the plan's front-matter line on the base, `riskFromFiles` over the base plan's file list, and `riskFromFiles` over every path the branch changed since its merge base, listed with `-z` and without rename detection so a file moved out of `src/auth/` still counts under its old name, leaving out only the task's own folder and `.reggie/journal/`. The report lists the files the plan never named. `riskFromFiles` and `reggie plan risk` are not changed.

**Check records (`checks.ts`).** One file per task, `.reggie/tasks/<slug>/checks.jsonl`, one JSON object per line, appended by one function, `recordCheck`, that the CLI verb and the MCP tool both wrap. JSON lines because a record carries arbitrary criterion text and notes, JSON escaping is unambiguous where the journal's markdown needed three rounds of forgery fixes, the web view and the report read it with `JSON.parse` and a schema check, and only the task branch ever writes the file, so it is never a file two writers share. A record holds `v`, `kind` (`criterion` or `review`), `key`, `outcome` (`pass` or `fail`), `evidence` (repo-relative paths), `note` (one line), `person`, `tool`, `session`, `at` (ISO instant), `head` (the commit the checkout was on), and for a criterion `n` and `text`, which are for readers and are never trusted.
- A criterion's key is `c:` plus the first twelve hex characters of the SHA-256 of its whole bullet, first line and indented continuation lines, whitespace collapsed; the second and later of several identical criteria get `#2`, `#3`. So renumbering or reordering changes nothing, rewording one word makes a new key, and an old pass cannot count for new words. `plan.ts` gains `planCriteria`, which walks the section once and gives each criterion its number, its one-line text and its key; `parsePlan` uses the same walk and returns what it returns today. A review's key is `r:` plus a name of lowercase letters, digits and hyphens.
- The verb is `reggie check <slug> <criterion> <pass|fail> [--evidence <file>…] [--note <text>]`, with `--review <name>` in place of the criterion; with no outcome it prints the report. The criterion is chosen by its number, its key, or a leading label such as `AC12` when exactly one criterion starts with it. It refuses, writing nothing: a selector that matches none or several (printing the numbered criteria with their keys), a slug with no plan, a checkout that is not on `task/<slug>` (records ride the branch), a criterion `pass` with no evidence, an evidence path that is not a non-empty regular file directly inside the task's evidence folder, and a `pass` while any tracked file outside `.reggie/` is modified, because a check proves committed code. `fail` is always recordable. It never commits, like `journal add`.
- The latest record per key wins, by position in the file and not by clock. A later fail supersedes a pass and a later pass supersedes a fail. A key that is in the file and not in the base plan can still be superseded by naming the key.
- Anyone who can commit on the branch can write a record by hand; the verb is a convenience, not a lock. What the evaluation verifies instead: the key must belong to a criterion of the plan on the base, every evidence path must resolve on the branch tip, and `head` must be an ancestor of the tip with no file outside `.reggie/` changed since, or the pass is stale and does not count. A line that is not a record (not JSON, not an object, over 16 KB, a wrong field type) is counted, named by line number, and is itself a refusal; parsed objects are rebuilt field by field, so a `__proto__` key goes nowhere.

**The packet's checklist is derived.** `reggie packet <slug>` writes the acceptance checklist between `<!-- reggie:checks:start -->` and `<!-- reggie:checks:end -->`: per criterion of the plan, `- [x]` only when the latest record passes, an `evidence:` line holding the record's bare paths, and a `check:` line with the outcome, who, the tool, the instant and the key, or "none recorded". The by-position evidence hint is deleted, which retires `reggie-packet-pairs-evidence-files-with-acceptan` and `the-packet-scaffold-pairs-each-acceptance-criter`; the build removes those two intake lines with `reggie plan done`. Run on a packet that exists, the verb rewrites only the text between the markers and says whether anything changed; a packet with no markers, written before this lands or by hand, is left byte-identical and said to predate check records. Typed in a checkout that is not on `task/<slug>` while that branch exists, it refuses and names the worktree, which closes the M13 trap. In this slice `reggie packet` never evaluates and never decides, and its last line says so.

**The packet contract (`lintPacket`, `reggie packet <slug> --lint`).** Front matter with the task's own slug and one of the three verdicts; the seven sections present, not empty, none still holding the scaffold's parenthesised stand-in (so Discovered issues says none or lists them); a generated checklist that equals what the records render; and every citation well formed. The human door does not run the contract; the report does.

**The evidence gate.** One parser in `packet.ts` serves the gate, the contract and the task page. A reference is the leading token of each comma- or semicolon-separated piece of an `evidence:` line or a `## Evidence` bullet, with backticks, brackets and parentheses stripped, plus whatever today's reader already returns, so nothing that links today stops linking and the captured prose-after-the-path item is retired by construction. A citation is a reference that names the task's own evidence folder, by full path or as `evidence/<name>`; other path-shaped words on those lines are prose, which is what keeps `src/c.ts` inside a parenthesis from being judged. Records carry citations as data and need no parsing. A citation resolves only to a regular, non-empty file directly inside `.reggie/tasks/<slug>/evidence/` on the branch tip: mode 100644 or 100755 from one `git ls-tree -r -z -l` of that folder on the resolved commit, under `--literal-pathspecs`. Refused, each with its own words: missing, empty, a symlink, a folder, a gitlink, a path in a subfolder (the evidence route serves flat names only), `..`, an absolute path, a backslash and a control character. The resolver itself never looks at a disk, so the report is the same wherever it runs; `reggie packet --lint`, which stands in the task worktree by design, adds for a missing file that is present there that it is on disk but not committed, because that is the surprise the brief predicts. An empty file fails although one honest empty diff exists in the record: with no reader, an empty file cannot be told from a redirect that failed, and the message says to save the command and its exit status into the file.
- **Both doors.** `landTask` runs the gate on the packet at the branch tip (or on the base for a task already landed) before anything is written, and a failure is a refusal naming every path and reason. That is the brief's "never passes, by policy or by hand". There is no override flag: fixing a citation is a one-line commit, and an override would make the gate advice. A packet with no citations at all still merges by hand exactly as today; checks, risk, plan edits and the contract bind the policy only. The web client shows the server's own sentence for a 409 from the decide route, since this adds a second reason that route answers 409 and the page must not blame a missing packet for it.

**One landing at a time (`land.ts`).** `landTask` takes a lock before its first check and drops it in a `finally`: a file created exclusively under the repository's common git directory, which every worktree shares, holding the pid, the slug and the instant. A lock whose pid is dead, or that is older than ten minutes, is replaced once; a live one is a refusal that names the other landing, with no waiting, because the server answers one request at a time. It refuses, without running `git merge`, when `MERGE_HEAD` already exists in the base checkout, and it calls `git merge --abort` only for a merge this call started. The brief put the merge out of scope; M10 is the reason this much of it is not.

**Discovered issues, captured inside the merge commit.** After `git merge --no-commit` succeeds and before the commit, `landTask` reads `## Discovered issues` from the packet now in the working tree and captures what is new into the merged `.reggie/intake.md`, staged with the verdict and the decide entry, so the landing, the verdict, the journal line and the captures are one commit and cannot disagree. If capturing throws, the existing handler aborts the merge and nothing is recorded. It runs on every solo approval, by hand now and by policy in the second slice, including the verdict commit of a task that had already landed; not on needs-work, where the packet goes back to its session with the section intact and a write into the base checkout would be the dirty tree M4 refuses; and not in team mode, which commits nothing and is deferred.
- A bullet is a top-level list item; indented lines and nested bullets under it become `>` detail lines. Skipped: the scaffold's stand-in, a bullet whose first word is none, nothing or n/a, and a bullet shorter than twelve characters.
- Already captured means any of: a backticked token, or the word after "captured as" or "captured:", that is a slug `knownSlugs` returns (intake lines, task folders, task and plan branches, so an item already triaged counts) or is one cut short or lengthened; the bullet's own slugified text being such a slug; or its normalised text equalling an intake item's. The comparison runs against the intake as merged, which already holds whatever the session captured on the branch. A duplicate is cheap and a loss is not, so a bullet reworded since its capture is captured again, and that limit is documented.
- The line is written by `capture()` with whitespace collapsed, invisible and control characters removed by the class `capture.ts` already exports, the text cut at 300 characters, at most ten detail lines of 500, the last detail line "Captured from the task `<slug>`" through the existing task origin, the source `packet`, and the handle from the task's claim record, else the packet's author, else the decider.

**The report (`policy.ts`).** `evaluateCompletion(root, slug)` returns the two commits, the policy and where it came from (the base commit's block, or the default for the mode when the block is absent), the three classes and the effective one with the unplanned files, each criterion as pass, fail, missing, stale or no-evidence with its record, each review, and the gates with their reasons: policy allows it, plan on the base, controls untouched, packet pending and in contract, every criterion passed and nothing failing, evidence resolves, risk within the class, merges cleanly. The last gate is `git merge-tree --write-tree` on the two ids; where git lacks it the gate says not checked and decides nothing. Not evaluated, each with its sentence: no `task/<slug>` branch, no packet on it, already decided, team mode, a base that cannot be named, a base config that does not parse. `reggie check <slug>` prints it, `--json` gives the object, exit 0 only for would pass, and the first line says it is a report and that a person decides. `GET /api/task/<slug>` carries the same object as `policy` for a task with a live branch and a packet; the task list does not evaluate. The task page draws it above the decide form.

**Config (`people.ts`).** A `policy` block with `plans` and `completions`, each `none`, `low`, `medium` or `high`. Absent or unreadable keys take the mode's default: solo `plans: high` and `completions: low`, team both `none`. `parseConfig(text)` is split out of `loadConfig` so the base commit's copy is parsed by the same code; `saveConfig` writes the block under a comment. This repository's file gains the block by hand, keeping every existing comment. `plans` is parsed and printed and nothing reads it yet: with the solo default every class is admitted, so the board must not change, and that is a bail check.

**Prompt and docs.** The build prompt tells a session to record each criterion with `reggie check` or the `reggie_check` tool after the code it proves is committed, to record each review, to list every unrelated problem under Discovered issues because an approval captures what the session did not, to re-run `reggie packet` until it says the checklist is current, and to read `reggie check <slug>` for what a decider will see. The generated block gains one sentence. The API contract, both guides, the README, the layout template, the DOM contract and the vision's 2026-09-15 bullet are brought into line, and the vision says what waits for the second slice.

**The second slice, settled here so that it is not re-derived.** It is captured as `policy-acts-on-its-verdict` and none of it is built now.
- The trigger. `reggie packet <slug>` evaluates when the packet already exists, the checkout is the task's worktree on `task/<slug>` with nothing uncommitted, and the packet, the records and a current checklist are in `HEAD`. The scaffolding run, `--force` and `--lint` never evaluate. `--no-policy`, or `REGGIE_POLICY=off` in the environment for a whole process tree, stops it and prints that the policy was not run, which is how a manager session keeps its own review gate. `reggie decide [slug] --policy [--dry-run]` is the standalone verb, from the integration checkout. Every not-evaluated and every refused outcome prints this slice's report.
- Where. The integration checkout is found as above and every write goes through its paths; an in-place claim is never landed by policy. A dirty base relays `landTask`'s sentence and adds that the session must not touch that checkout. Release runs last; the session is told its directory is gone and to `cd` to the integration checkout. Measured: the process survives the deleted directory, so nothing may call `process.cwd()` after the release.
- Failure. The verdict, the decide entry and the captures stay inside the merge commit, so a conflict records nothing and the task stays awaiting decision with the reason on its page; a failed release leaves a landed task with a branch to release by hand; a re-run finds it already decided and writes nothing.
- The actor. `decided_by: policy` and `decided_for: <handle of the person whose checkout ran it>` in the packet, `Decided-by: policy` and `On-behalf-of:` in the merge commit, a decide entry under that person's name with the tool `policy`, the handle `policy` never generated for a person, `decidedFor` in the API, a chip and a story sentence that do not link a person. A hand decision is unchanged.
- Plans. A plan that passes by policy records nothing and changes nothing on the board; writing `decided_by` into a plan would dirty the base to store a fact the state derivation already reads from the class and the key. The key matters only once narrowed: a plan above it stays groomed with the reason, and `reggie decide <slug> approved` on a task with no packet records `approved_by` and `approved_at` in the plan's front matter.
- In practice it also needs the intake file to stop conflicting (M5), which is captured separately.

Rejected alternatives. Building it as one task, as the decision's wording suggests: the preconditions still land before anything acts on them, and the decision's reason, that approval without a person is only safe once all four hold, is kept. Reading the risk or the policy from the branch: M6 and M7. Trusting the plan on the branch when it differs from the base: a reworded criterion is a deviation a person should see, and it happened on one landed task in fifteen. Parsing every path-shaped token in a packet as a citation: measured, it judges prose. Accepting an empty evidence file: see above. A markdown or YAML check log: a second forgeable text format and a new parser. Keying a check by criterion number: renumbering would move a pass onto other words. A timestamp order for records: clocks differ and git already orders the file. Storing the verdict of an evaluation in the repo or the cache: it is a function of two commits and is recomputed. Waiting on the lock: the server is single-threaded. An override flag on the human door: it turns the gate into advice. Capturing on needs-work: nothing is lost yet and the write dirties the base. Changing `DEFAULT_RISK` to cover manifests and workflows: the brief rules the risk rules out of scope, so the control files are a fixed list inside the policy and the rest is the owner's existing `risk` knob.

## Assumptions
- Plans of every class pass in solo mode and completions pass at low only. Answered by jacobpress on 2026-09-15; binding, and it reverses the brief's paragraph on medium and high plans, which is not planned. The `plans` key exists so the owner can narrow it, with a solo default of `high`.

## Bail conditions
- If the evaluation cannot be made a function of two commits, and needs either working tree for anything but choosing which checkout's config names the base branch, stop: the safety case rests on that property.
- If the evidence rule, run over the fifteen landed packets, reports any citation missing or refuses more than the one empty file, stop and re-plan the rule; a gate that refuses honest packets gets switched off.
- If enforcing the evidence gate on the human door breaks any existing landing or decide test for a reason other than that test's own packet citing an unsaved file, stop: the human door is then not as it was.
- If the task list of this repository differs in slug, state, reason or risk before and after the change, stop: nothing in this slice may move a card.
- If the new evidence reader returns fewer references than today's for any landed packet, stop; the task page would lose links it shows today.
- If the lock cannot be made safe against a holder that crashed without waiting or polling inside the server, stop and re-plan it; an approval that hangs the single-threaded server is worse than the race.
- If an honest flow (commit the code, verify, record, scaffold the packet, commit) cannot produce a would-pass report in the end-to-end fixture because of the staleness rule, stop and bring the rule back to the owner rather than loosening it quietly.
- If capturing inside the merge commit cannot be done without a second commit, or makes any existing landing test's merge commit differ in anything but the intake file, stop; one commit is what keeps the verdict and the landing from disagreeing.
- If any step needs `reggie decide` to be run against this repository, or a probe to run outside the OS temp directory, stop.
