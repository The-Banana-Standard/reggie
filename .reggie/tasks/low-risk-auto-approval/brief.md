# Low-risk plans and completions pass by policy in solo mode

## Problem
Every task built through the loop ends the same way: a build session runs `reggie packet <slug>`, ticks the acceptance criteria by hand, commits the packet on the task branch, and then stops and asks a person to type `reggie decide <slug> approved`. In solo mode that person is the same one who wrote the plan, launched the session and will read the diff later anyway, so for a low-risk task the decision is a formality that still costs a sitting at the keyboard and a merge typed by hand. The 2026-09-15 decision is that in solo mode low-risk plans and completions pass by policy, on the stated assumption that anything a human would not have approved surfaces later as a discovered issue and becomes the next task. The decision names four preconditions and asks for them as one task, because a policy that approves without a human is only safe once each of them holds.

The first precondition is an evidence gate. Today nothing checks that the evidence a packet cites exists. `scaffoldPacket` lists whatever is under `evidence/` and writes an `evidence:` hint under each criterion, but the session fills those lines in free text, and `decidePacket` only rewrites three front-matter fields; there is no packet linter at all, though the vision names one beside the brief and plan linters. A packet can claim a test passed and point at a file nobody saved, and a human reader is the only thing that would notice. The gate is a packet contract: every evidence path cited under a criterion or under the Evidence heading must resolve to a file on the ref the packet was read from, and a packet that fails it never passes, by policy or by hand.

The second is that checks are recorded as data rather than as a ticked box. A packet's criteria are `- [ ]` lines a session ticks by editing markdown, so the record of what was verified is a character in a file. The decision asks for a `reggie check` verb, which does not exist; the only `check` today is `reggie docs check`, a CI gate for generated blocks. A check is a named criterion or review with an outcome, the evidence that proves it, who or what ran it and when, appended as a record under the task folder; the packet's checklist is then derived from those records and the policy reads the records, not the ticks. Unlike `decide`, `check` is exactly the kind of verb a build session runs, so it is a CLI verb and an MCP tool that wrap one function, as the 2026-09-15 block requires of every session-facing verb.

The third is that Reggie owns the merge. `reggie decide approved` writes a verdict and prints "commit it and merge the task branch"; no merge call exists anywhere in `packages/reggie/src`. That half is already assigned to `task-attribution-by-merge`, which lands before this item and gives `decide approved` the `--no-ff` merge in solo mode with an abort that leaves both branches untouched. This item depends on it and adds nothing to the merge itself: the policy path calls the same function a human approval calls, so the first automatic landing goes through a merge a person has already watched work.

The fourth is that the packet's discovered issues are captured into intake automatically. The scaffold's Discovered issues section only asks the session to run `reggie capture` for each one, and the build prompt repeats the request. Once nobody reads the packet before it lands, an issue a session wrote down and never captured is lost, and the whole safety argument of the decision rests on those issues becoming the next task. So an approval, by policy or by hand, reads the section and captures each bullet that is not the placeholder and not already an intake line, attributed to the session that found it.

Two things the note asks this brief to settle. The policy's shape in `.reggie/config.yaml` is a `policy` block with two keys, `plans` and `completions`, each naming the highest risk class that passes without a person: `none`, `low`, `medium` or `high`. Solo mode defaults both to `low` and team mode defaults both to `none`, so the file says in one place what the mode preset means and a person can turn the policy off or widen it without editing code. `loadConfig` ignores unknown keys today, so the key is additive, and `saveConfig` learns to write it. When it runs: as an explicit pass from the integration checkout, never from inside a session, because `decide` is never a session tool and because the merge lands on the default branch where the serving checkout already is. The pass walks every task whose state is awaiting-decision or whose plan passes the contract, applies the policy to those at or under the configured class, records `decided_by: policy` in the packet or plan front matter and a journal entry at stage decide, and performs the merge for completions. It is a verb first, `reggie decide --policy` over all eligible tasks or one slug, and `reggie serve` may call it once it is trusted, the same shape the 2026-09-15 block chose for the derived journal. The risk class it reads is the one the plan's front matter carries, set by `reggie plan risk` from the path rules; the decision keeps that proxy until the class derives from the graph.

The second thing to settle: whether medium and high plans still pass on disk in solo mode, as every lint-passing plan does today. They do not. Today `tasks.ts` counts any plan on disk that passes the contract as planned in solo mode, whatever its risk, which was the right rule while a person sat in every planning session and accepting the plan in plan mode was the approval. Once the loop plans unattended, a lint-passing plan on disk proves only that a session finished, and a policy that says low-risk plans pass is empty if medium and high pass anyway. So in solo mode a medium or high plan on disk stays groomed with a reason saying it waits for the owner's approval, and the owner approves it with the same `reggie decide <slug> approved` act, which learns to record a verdict on a plan when the task has no packet yet. This changes the board for every loop-planned item above low and is the one settlement here that reverses current behaviour rather than adding to it; it is called out again under Open questions so it can be reversed cheaply if the reading is wrong.

## Why now
The loop runs unattended now: the same 2026-09-15 block moves planning entirely into sessions, adds an idea action that shapes an item the moment it strikes, and captures a queue of loop-plumbing tasks that are being built one after another. Each of them ends at a packet waiting for a keystroke, so the throughput of the whole loop is currently the number of times a day Jacob sits down to type `reggie decide` and a merge command. Low-risk items are most of the queue, and they are exactly the ones the decision says need no sitting.

The order matters too. `task-attribution-by-merge` lands first and gives `decide` the merge; the needs-you queue lands after and lists what waits on a person. If this item lands between them, the queue's first version shows only the decisions a human genuinely owes, instead of a column of low-risk packets that policy could have closed. Landing it later means the queue is built against a decision list that is about to shrink.

It also gets riskier to wait. Every packet that lands today lands with hand-ticked criteria and free-text evidence claims that nothing verified, and the discovered issues written into those packets are being captured only when a session remembers. The evidence gate and the check records make the packets already in flight honest whether or not the policy ever approves one; the auto-capture stops the loss of exactly the issues the decision's safety argument depends on.

## Suspected area
- packages/reggie/src/packet.ts because `scaffoldPacket`, `parsePacketVerdict`, `locatePacket` and `decidePacket` are the packet as it exists, and the evidence gate is a packet linter that does not exist yet beside them; the policy's approval and a human's approval both end in `decidePacket`
- packages/reggie/src/cli.ts because `reggie decide` is the verb that grows `--policy` and a plan verdict, `reggie check` is a new top-level verb next to the existing `docs check` subcommand, and `reggie packet` prints the instruction to tick criteria that this item retires
- packages/reggie/src/people.ts because `ReggieConfig`, `loadConfig` and `saveConfig` define what `.reggie/config.yaml` may say, and the `policy` block with its per-mode defaults lands there
- packages/reggie/src/tasks.ts because the planned rule for solo mode lives in the state derivation and in `STATE_MACHINE`, both of which currently say a passing plan on disk is enough, and because the policy pass needs the same list of awaiting-decision tasks the board reads
- packages/reggie/src/plan.ts because a plan verdict for medium and high plans has to live in the plan's front matter next to the `risk` line `setPlanRisk` writes, and `parsePlan` has to read it back
- packages/reggie/src/capture.ts because the discovered-issue auto-capture is `addToIntake` called per bullet, and the duplicate check against existing lines belongs beside `readIntake`
- packages/reggie/src/mcp.ts because `check` must be reachable from a build session without a shell PATH, and the tool wraps the same function as the CLI verb
- packages/reggie/src/launch.ts because the build prompt tells a session to fill the packet and tick criteria, and after this item it tells the session to record each check and cite the evidence the gate will verify
- packages/reggie/src/serve.ts because the `/api/decide` route is the second human door onto the same approval and merge path, the board's state reasons change for medium and high plans, and the policy pass may later run from the server

- packages/reggie/src/paths.ts because the check records need a path under the task folder next to `packet.md` and `evidence/`
- packages/reggie/docs/ui-api-contract.md because the decide route's contract, the state rules a page renders and the reason strings all change
- docs/how-reggie-structures-a-repo.md and docs/getting-started.md because both describe the solo-mode state rules and the packet-then-decide ending of a task
- .reggie/config.yaml because this repo's own file gains the `policy` block and its header comment describes what solo mode means

## Open questions
- Is the settlement on medium and high plans the intended reading? The 2026-09-15 block says low-risk plans pass by policy and says nothing about the others; this brief infers that they therefore wait for an explicit approval and stop counting as planned on disk in solo mode. If the intent was that a person's own plan is always implicitly approved and the policy only matters for completions, the plan half of the policy becomes a no-op and the `plans` key should go.
  > Answered by jacobpress on 2026-09-15: No. In solo mode plans of every risk class, low, medium and high, pass by policy; whether high should be removed is judged as we go. Completions pass at low only.
- What does a plan approval look like as data? The brief settles that it is recorded on the plan itself through `reggie decide`, but the vision also speaks of plan packets decided like completion packets; whether a plan gets a verdict block in its front matter, a sibling file, or a packet of its own decides how much of the packet code the plan path reuses.
- What is the file format of a check record? One record per line in a `checks.jsonl`, an append-only markdown list like the journal, or YAML; the choice decides whether the web view and the derived journal can read them without a new parser, and whether a session can write one without the verb at all.
- Is a check the unit of a criterion, of a review, or both? The plan's acceptance criteria and the review policy by risk class are both things a packet claims to have done; if both are checks, the record needs a kind, and the policy needs to know which kinds are required at which risk class before it approves.
- Which checks must be present for the policy to approve a low-risk completion: every criterion in the plan with a passing outcome, or merely no failing one? Missing checks and failing checks are different states, and a session that recorded nothing should probably not pass.
  > Answered by jacobpress on 2026-09-15: Every plan criterion has a passing check and no check of any kind fails. A packet with no checks never passes.
- What does the evidence gate accept as a citation? The scaffold writes `evidence:` lines under criteria and bullets under Evidence, but sessions also write paths in prose; whether the gate parses only the structured lines or every path-shaped token decides how many honest packets it rejects.
- Where does the gate resolve evidence paths? The packet is usually read from `task/<slug>` while the checkout is on the integration branch, so the files must be checked on that ref rather than on disk; an evidence file the session forgot to commit is then a failure, which is right but will surprise the first session it happens to.
- What is the actor of a policy decision? The brief settles `decided_by: policy`, but the journal, the board and the packet's Decision section all render a person; whether the entry also names the machine owner whose config allowed it, and how a policy decision is told apart from a human one in the Completed view, is open.
- When exactly does the policy pass run before `reggie serve` is trusted to call it? The loop script after a build session ends, a person typing the verb, or a cron are all consistent with the settlement, and they leave different windows during which a low-risk packet sits at awaiting-decision.
  > Answered by jacobpress on 2026-09-15: Inside reggie packet, so a session that writes its packet triggers the evaluation and, on a pass, the merge; plus a standalone verb by hand. A serve pass may call it later once trusted.
- How are discovered issues deduplicated? A session that followed the prompt already ran `reggie capture` for each one, so the auto-capture will meet bullets that are intake lines already; matching by exact text, by slug, or by a marker the session leaves is unsettled, and the placeholder bullet must be skipped.
- Does the auto-capture also run on a human approval and on a needs-work verdict? The decision names it as a precondition of the policy, but an issue a human approver did not capture is just as lost, and a needs-work packet may carry issues worth keeping even though the task goes back.
- What happens when the policy approves and the merge aborts on a conflict? The verdict and the merge are two steps; whether the packet keeps `pending`, records `approved` with the merge outstanding, or the task shows a new reason on the board decides what the owner sees the next morning.
- Does the policy apply to a task whose plan was approved by policy and whose completion is also low risk, end to end with no human in the loop at all, or should at least one of the two decisions always be a person's while the risk class is still the path-rule proxy?
- Should the `policy` block accept overrides finer than a risk class, such as a per-area allow list or a file-count cap, given that the path rules already count more than twelve files as medium? The brief settles a class per packet kind and nothing else.
  > Answered by jacobpress on 2026-09-15: No. One class per packet kind, the single knob slated to derive from the graph later.
- Does team mode ever run the policy from the repo, or is auto-approval there the GitHub side of the vision's borrowing table, a bot or a ruleset? The brief settles that team mode defaults to `none` and says nothing further.
  > Answered by jacobpress on 2026-09-15: Not now. Team mode is deferred until the loop works for one person.

## Not this
- The merge itself. `task-attribution-by-merge` owns the `--no-ff` merge, the conflict abort, the merge commit's message and the first-parent join; this item depends on it, calls the same function, and adds nothing to what the merge does.
- The needs-you queue. It lists what waits on a person, and this item shrinks that list; the rows, the decision cards and the layout are the queue's own task.
- Risk class from the graph. The decision keeps the path-rule proxy; making the class derive from imports, ownership or history is the later item the vision names as the thing that decides how far the policy can be trusted.
- `packet` and `pr` as MCP tools. That is `mcp-packet-and-pr-tools`; this item adds `check` as a session tool for the same reason but does not move the other two.
- Team-mode approval through GitHub. Required reviewers, rulesets and a bot approving low-risk pull requests are the borrowed half of the vision's table and are not built here.
- Any change to what a plan or a brief must contain. The plan contract, the brief contract and `reggie plan risk` are taken as they stand; this item adds a packet contract beside them.
- The derived journal. A policy decision writes a journal entry the way a human one does today; deriving entries from transcripts and commits is `derive-the-journal`.
- Retiring the intake line at triage or the six slash commands. Both are neighbouring 2026-09-15 items and land separately; the auto-capture here writes intake lines through the same `capture` door they leave in place.
