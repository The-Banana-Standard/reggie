# An idea action on every page that captures a line and opens a shaping session with the page's entity in the context pack

## Problem
The 2026-09-15 decision says every page gets an idea action: capture a line, mint the slug, open a shaping session in plan mode with the page's entity as context. The web view has both halves and nothing joins them, and neither half knows where the reader was. Measured on 2026-09-18 against a probe server on a throwaway repo, read-only, before this plan was written:

- **The routes today.** `POST /api/capture` mints the slug, stamps `web` and appends the line; a body carrying `path` or `symbol` is answered 200 and the fields are dropped without a word. `POST /api/launch` and `reggie launch --run` both build every pack from `{ slug }` alone, and `GET /api/launch?path=` ignores the parameter. `LaunchInput` has no field a path could travel in.
- **What `buildContext` does with a path.** For a fresh slug with no path the pack is the repo facts line, "Plan: none yet", the `_repo` note and the working agreement, and nothing else: no intake line, no detail. A folder path (`src/lib`, with or without a trailing slash, with or without a leading `./`) adds the folder's note chain (`_repo`, then `src/lib/`), the folder under "Files in scope", the commits that touched it and the tasks whose plans overlap it. A file path adds the file's own note and its commits the same way. A path with a space (`src/a b.ts`) and one with non-ASCII letters (`src/café ü/uni.ts`) both pass through untouched. A path that does not exist is listed as "(does not exist yet)" and then, because the missing file is filtered out before `git log` runs and the argument list is left empty, the section "Recent commits touching these files" holds the last ten commits of the whole repo: a pathspec-magic string (`:(exclude)src`) and a glob (`src/*.ts`) do the same. A `..` segment or an absolute path throws from the note resolver, which a route would answer 500 unless it validated first. A symlink whose target is outside the repo (`docs/outside` → `/etc/hosts`) is accepted, and so is `.git/HEAD`; neither reads a file, but neither is an entity of the repo either.
- **What a launch does when Terminal cannot open** (measured with the osascript call stubbed at the `child_process` level, never with a real window). A denied automation prompt (exit 1, "Not authorized to send Apple events to Terminal") comes back in 0 ms as `launched: false` with the reason, the full command, the session id and the resume command; a hung osascript comes back after the 8 s bound with the "did not respond within 8 seconds" reason; a Codex launch has `session: null` and `resume: "codex resume --last"`. The POST route then records the launch and answers 200 whatever `launched` says, so a launch that opened nothing still leaves a record whose session id names a transcript that will never exist (pre-existing; captured, not fixed here). On a non-macOS platform the answer is the same shape with the "only on macOS" reason, which is the branch the test suite already exercises.
- **How the prompt reaches a shell.** The prompt is one element of `argv`; `command` is `argv.map(shellQuote).join(" ")`, and the only shell quoting in the product is that function: bare when the word is `[A-Za-z0-9_@%+=:,./-]+`, else single quotes with `'` written as `'\''`. Measured with a note holding `'`, `$(`, backticks, `;`, `&`, `|`, `>`, `\` and `"`: every one of them is inside the single quotes, and the AppleScript layer then doubles backslashes and escapes double quotes. A path in the prompt is quoted exactly as the note is today.
- **What the client does when a launch fails.** `makeLauncher(ctx).run` treats `launched: false` as a normal answer: a warning toast with the reason and the command handed to `onCommand`, which draws a readonly field with a Copy button; a thrown POST (500, network) toasts the error and fetches the command from `GET /api/launch` for the same field. `launchAction` disables its buttons while the request runs and after six seconds hands over the command with a "still waiting for Terminal" sentence. Nothing in either helper knows about a capture, so a capture that succeeds and a launch that fails is today two unrelated things on two different pages.
- **The header has no slack.** At 1440 px wide the repo page's header holds the brand (93 px), the breadcrumb (202 px, already one pixel short of its title), the four-item nav (350 px) and the tools (715 px); the free space between the breadcrumb and the nav is 16 px. On a file page the tools grow to 784 px (the Code pane toggle) and the breadcrumb shows 133 of its 220 px. At 390 px the header is the brand mark (33 px), the breadcrumb (117 of 195 px), then Map (49 px), Search (36 px) and, in workspace mode, the repo switcher (107 px), with 8 px free. Whatever is added to the header is paid for by the breadcrumb, which already ellipsises.
- **The workspace page's repo cards.** Each `.ws-tile` is an `<a>` of 260 by 157 px in the map column under the canvas, so a button cannot go inside it as it stands (interactive content inside a link), and on a phone the whole strip is behind the header's Map button; the story's Repos section is what a phone shows.
- **Capture's edges.** Whitespace-only text is refused 400 "text is required". A newline in the text collapses to a space, and every line of `detail` becomes its own `  > ` line, so neither can forge a second intake item. A 200-character line gets a 48-character slug and the whole text on the line. Text equal to an existing task's title mints `<slug>-2`. Emoji-only text mints `item`. Text holding `[[#/x|y]]` is kept verbatim and the task page renders it as an in-app link (pre-existing). A repo with no `.reggie/` at all accepts a capture: `.reggie/intake.md` is created with the header and the person is read from git config.
- **Where a detail line is already shown.** The task page's "What was written" section renders every detail line as a paragraph through the story's link markup, and the board card's detail panel renders each through `inline` (backticks become code). A detail line naming the entity is therefore visible on both before the item is shaped, with no new rendering, and triage's scaffold copies the line and its detail into the brief's Problem.
- **Baseline.** `TZ=UTC npx vitest run` is 1022 passed and 1 skipped; `npm run typecheck` prints nothing after the tsc line.

## Approach
Extend the two routes that exist, compose them from a new client module behind one header button, and make the entity travel both ways: into the intake item as a detail line written by `capture()` itself, and into the pack as a `paths` field on `LaunchInput`. No new route, no new launch mode, no story change, no Spotlight change.

**One resolver for the origin (`capture.ts`).** `resolveCaptureOrigin(root, raw)` is the only place a page path is accepted, and every door (`POST /api/capture`, `GET`/`POST /api/launch`, `reggie capture --path`, `reggie launch --path`, `reggie_capture`) calls it. It takes `{ path?, symbol?, task? }` and returns `{ kind: "file" | "folder" | "symbol" | "task", path?, symbol?, task? }` or throws a sentence of Reggie's own. A path passes `safeRepoPath`'s rules (trimmed, no NUL, no backslash, one leading `./` dropped, not absolute, no `..` segment), then loses trailing slashes, is refused when it is empty or `.` (the repo itself is the absence of a path), when it holds a control character, or when it holds any of `` ` ``, `[`, `]`, `|` (the four characters that could forge a code span or a `[[route|label]]` link in the two renderers of a detail line), and must then be an exact member of `git ls-files --cached --others --exclude-standard` (a file, or a symlink git tracks) or a prefix of one followed by `/` (a folder), the same listing the code map is built from; that is what refuses `.git/HEAD`, an ignored path such as `.reggie/.cache/…`, a glob, pathspec magic and a deleted file, before any of them can reach `git log`. It must exist on disk, and its real path must stay under the repository's real path, which refuses a symlink that points outside. `symbol` is allowed only with a file path and must match `^[A-Za-z_$][A-Za-z0-9_$]{0,199}$`. `task` is allowed only without a path, must pass `isSafeSlug`, and must be in `knownSlugs`. The listing costs one `git ls-files` per capture; measured at 31 entries on the probe repo and 235 on this one, which is nothing against a write.

**The detail line (`capture.ts`).** `CaptureInput` gains `origin?: CaptureOrigin`, and `capture()` writes it as the last `  > ` line under the item, after any detail the person gave, through one exported `originLine(origin)`: `` Captured from the file `src/serve.ts` ``, `` Captured from the folder `src/lib` ``, `` Captured from `launchSession` in the file `src/serve.ts` ``, `` Captured from the task `derive-the-journal` ``. The path is printed exactly as the resolver tidied it (no trailing slash, the same spelling the pack's "Files in scope" uses). The `source` stamp stays `web`, `cli` or `mcp`: the stamp is a fixed vocabulary the board draws as a chip and the intake parser reads between commas, and a path can hold a comma. Nothing else about the line changes, so the intake parser, the remover, triage's prefill and both renderers read the new line without learning anything. The resolver runs before the file is touched, so a refused origin writes nothing.

**The pack path (`launch.ts`, `serve.ts`, `cli.ts`).** `LaunchInput` gains `paths?: string[]`. `launchCommand` stays pure: it refuses an empty entry, a control character, more than eight paths or a path over 512 characters, and adds one sentence to every goal's prompt after the context clause: `` The pack was also built around `src/serve.ts`: its notes, its recent commits and the tasks that touch it are in there, so start reading at that place. `` (several paths are joined with "and"). The paths reach `command` the way the note does, as part of the single-quoted prompt. Both callers pass the same list to `buildContext(paths, config, { slug, paths })`, after resolving each entry with the origin resolver; `recordLaunch` is unchanged. `parseLaunch` in `serve.ts` reads `paths` (and `path`, singular, the way `slug` stands in for `slugs`) for POST and the repeatable `path` parameter for GET, so the tooltip and the copy field show the same command the launch would run.

**The client (`ui/idea.js`, new).** One module owns the header trigger, the popover and the capture-then-launch sequence, and app.js and the workspace tiles call it. `originFor(route)` maps the route to the body: repo, tasks, services, flows, flow, people, person and time give the repo alone; area gives `path: route.id`; file gives `path`; symbol gives `path` (the file part of the id) and `symbol`; task gives `task: route.id`; workspace and home give nothing, and the trigger is hidden there. The trigger is a `.btn` in `.header__tools`, first in the row, with a new `idea` icon and the label "Idea" that hides below 1500 px, because the header is measured full at 1440 and the 36 px of an icon button is the least the breadcrumb can lose. Clicking it opens `.idea`, a `role="dialog"` popover placed under the button on desktop and full width under the header on a phone, holding one sentence saying where the idea will land ("Into reggie, from the file `packages/reggie/src/serve.ts`"), one input, a main button reading "Capture and shape in Claude Code" (the remembered tool) with a caret naming both tools, and an error line; Cmd or Ctrl and Enter submits, Escape closes through the existing unwind chain, focus goes to the input on open and back to the trigger on close. On submit the form disables itself and posts `/api/capture` with the text and the origin; on 200 it toasts "Captured as `slug`", invalidates the cache and redraws the level, then hands `[slug]` and the path to `makeLauncher(ctx).run` in `discuss` mode, which is the launcher the board already uses and which resolves the goal on the server (an ungroomed slug is shaped). `run` and `describe` gain `paths`. Three outcomes, all inside the popover so the reader never has to find the board: `launched: true` on a loopback page closes the popover behind the launcher's own toast; `launched: true` on a page that holds a serve key keeps the popover open with a link to the new task, the sentence that the session opened on the machine running `reggie serve`, and the command in the copy field, because the window is on another machine; `launched: false`, a thrown launch or a launch that runs past six seconds keep the popover open with the link to the new task, the server's reason (or the "still waiting" sentence), and the command in the copy field, exactly as the board's launcher already does through `onCommand`. When even `GET /api/launch` cannot answer, the field holds `reggie launch <slug> --run` and a sentence naming the path to add with `--path`. The text of the idea is never sent to the launch: the launch body holds the slug, the tool, the mode and the path, so the captured words reach the intake file and nowhere near a command line. On the workspace page each `.ws-tile` becomes a `div` wrapping the existing link (`a.ws-tile__link`) and a `.ws-tile__idea` button that opens the same popover for that repo with no path. `board.js` exports `makeLauncher`, `commandField`, `friendlyError`, `TOOL_LABEL` and `rememberTool` so the new module composes what exists rather than copying it.

**The CLI and the MCP tool.** `reggie capture <text> --path <path>` takes one path (a file or a folder) beside `--detail` and `--slug`, and writes the origin line after the person's detail; `reggie launch <slug...> --path <paths...>` resolves each path, prints the clause in the command without `--run`, and with `--run` builds each pack around the paths. `reggie_capture` gains an optional `path`, validated by the same resolver, and a refusal is a tool error. No MCP launch tool, by the owner's ruling.

**A dev harness for the browser.** Nothing under `ui/` has an automated test, and a real launch opens a Terminal window, which no build or review session may do. `ui/dev/serve-idea-fixture.ts` builds a fixture repo (notes on a folder and a file, a file with a space and one with non-ASCII letters, a symlink out of the repo, three tasks in different states) and starts `startServer` from `src/serve.ts` with the osascript call replaced at the `child_process` level, in one of three modes chosen by `IDEA_TERMINAL=ok|deny|hang` (default `deny`): `ok` answers exit 0 without opening anything, `deny` answers the "Not authorized" error, `hang` never answers so the 8 s bound fires. It prints the root and the pages worth opening. Every browser criterion below runs against it; the success path with a real Terminal window is left to the owner and said so in the packet.

**Docs.** `docs/ui-api-contract.md` documents the three capture fields and the `origin` echo in the answer, `paths` and `path` on both launch routes, and the resolver's refusals and their sentences; `docs/ui-spec.md` gains the header button in §3.1, the tile button in §2 Level 0, and one subsection for the flow; `ui/DOM-CONTRACT.md` gains the id, the classes, the module and the icon; the package README gains the two options.

Rejected alternatives. One combined route that captures and launches: it would be the first route doing two writes, it hides which half failed behind one status, and the CLI would still need both options separately; the sequence is safe as it is because `POST /api/capture` clears the repo's caches before it answers, so the launch that follows rebuilds the task list and finds the slug (measured: the 10 s TTL never applies after an invalidate). Deriving the pack path at launch time by parsing the detail line back: elegant, but it couples a prose line to a parser, which is the drift the intake notes warn about; the client and the CLI hand the path over explicitly instead. A story action (the brief's sketch): the owner ruled the header and the Spotlight untouched, so `story.ts` and `story.js` are not changed. Sending the captured line as the launch note so the session sees the words at once: it would put the person's text on the shell line for no lasting gain, since `context-pack-omits-intake-line` is what puts the line in the pack. A repo picker in the header on the workspace page: the owner put the action on the cards. A `source` stamp naming the page: a path can hold a comma and the stamp sits between commas.

## Acceptance criteria
- [ ] AC1 `resolveCaptureOrigin` accepts a file (`src/serve.ts`), a folder written as `src/lib`, `src/lib/` and `./src/lib`, a file with a space, a file whose path holds non-ASCII letters, and a symlink that git tracks whose target is inside the repo, and returns the kind and the tidied path (no leading `./`, no trailing slash) for each.
- [ ] AC2 `resolveCaptureOrigin` refuses, with a sentence that holds no absolute path, each of: an empty path, `.`, `./`, an absolute path, a path with a `..` segment, a backslash, a NUL, a newline, a tab, a backtick, `[`, `]`, `|`, `.git/HEAD`, a path under an ignored directory (`.reggie/.cache/x`), a glob (`src/*.ts`), pathspec magic (`:(exclude)src`), a file that is in the index but no longer on disk, a file that was never in `git ls-files`, and a tracked symlink whose target resolves outside the repo; after each refusal `.reggie/intake.md` is byte-identical to before.
- [ ] AC3 `resolveCaptureOrigin` refuses a `symbol` without a path, a `symbol` with a folder path, a `symbol` that fails `^[A-Za-z_$][A-Za-z0-9_$]{0,199}$` (a space, `::`, `<script>`, 201 characters), a `task` given together with a path, a `task` that fails `isSafeSlug`, and a `task` no task in the repo carries.
- [ ] AC4 `capture()` with an origin writes exactly one added detail line, the last `  > ` line under the item, reading `` Captured from the file `src/serve.ts` ``, `` Captured from the folder `src/lib` ``, `` Captured from `launchSession` in the file `src/serve.ts` `` or `` Captured from the task `<slug>` ``; the intake line itself is byte-identical to one captured without an origin; a `detail` given beside the origin is written first; `parseIntake` reads the line and its detail back, `removeFromIntake` removes both, and `scaffoldBrief` copies the origin line into the brief's Problem.
