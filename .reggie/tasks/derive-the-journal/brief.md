# Derive the journal from session transcripts and commits with an explicit verb

## Problem
The journal is the narrative the web view tells about the work, and today it only exists if a session remembers to write it. The generated instruction block and every context pack end with the same request, one plain-English entry after each step, and the record is whatever the sessions felt like leaving: the shaping sessions on 2026-09-15 wrote long, careful entries, build sessions write at whatever granularity they choose, and a session that forgets leaves a task with a claim, some commits and a packet but no story between them. The 2026-09-13 decision names the fix: the journal is derived, not remembered. Everything the entry should say already exists on disk. Both tools leave a transcript, the task branch carries the commits, and the state transitions (claim, plan, packet, verdict) are already read from git and the task folder. Reggie should read those and write the entry itself, in listener register, attributed to the person and the tool, with the evidence linked, and a person or a session may still add an entry by hand when the transcript does not say what mattered.

The 2026-09-15 decision settles the trigger, which was an open fork: an explicit verb, `reggie journal derive <slug>`, that works for a task in flight and for a completed one. A session-end hook was rejected because it is per machine and Codex has none; a pass inside `reggie serve` may call the verb later, once it is trusted. For a task in flight the verb reads the branch's commits and the live transcript; for a completed one the branch is usually gone, so the commits come from the merge commit, which is what `task-attribution-by-merge` makes findable. The verb can be run more than once for the same task as work continues, so it must never repeat what an earlier entry already said.

Finding the transcript is the part that is half built. For Claude, `launch` mints a session id, passes it to the tool as `--session-id`, and records it in the claim file and in the launch record under the cache folder together with the tool, the goal, the start directory and the time; the transcript lives under the home `.claude/projects` folder in a folder keyed by the encoded start directory, named by that id, with the working directory on each message. For Codex, `launch` mints nothing; the transcript lives under the home `.codex/sessions` folder by date, with the working directory in its session metadata, so a Codex session is matched by directory and time rather than by id. Sessions that were not started by `launch`, and every claim or entry written from inside a session, currently record the word `session` where an id should be: `sessionName` reads an environment variable that nothing sets. The precursor named in the intake note is for `sessionName` to read the real session id (the variable that names the transcript file, not the host's own id), so a claim made from inside a session points at its transcript the same way a launched one does.

On this machine the transcript layout is not exactly the flat file the intake note describes. The project folder for this worktree currently holds only a folder named by a session id, with a `workflows` folder inside it, and no transcript file at the top level; the parent checkout's folder holds a session-id folder and a memory folder. So the verb has to be built against what a launched session actually writes, checked on this machine, rather than against the path in the note.

## Why now
The 2026-09-15 order puts loop plumbing first and lists the derived journal near the end, after the stale bin, the journal union-merge line, attribution, worktree dependencies, the small items and the branch diff, and before the queue. It belongs there because two of the earlier items are explicitly stopgaps until this lands: the `.gitattributes` union line is "until the derived journal replaces hand-written entries", and the generated instruction block keeps asking for one entry per step "until the derivation is built". Both of those debts are paid here or carried forever.

What gets worse while it waits is the record itself. Every session that runs before this lands leaves a transcript nobody reads and a journal only as good as the session's habit, and the transcripts do not stay: the tools keep them under the home folder, outside the repo and outside git, subject to whatever retention the tool applies, so a task landed months ago will have commits but no transcript to derive from. The longer the derivation waits, the larger the stretch of history that can only ever be narrated from commits. The precursor is also cheap and independently useful: while `sessionName` says `session`, every claim made from inside a session and every day file share one name, which is the collision the union-merge item is currently papering over.

## Suspected area
- packages/reggie/src/journal.ts because `sessionName`, `journalFile`, `appendJournal` and `parseJournalFile` are the whole of how entries are named, written and read back, and derive is a new writer that has to live beside them and be recognisable when the file is read again
- packages/reggie/src/launch.ts because it mints the Claude session id, passes it as `--session-id`, and writes the launch record with the slug, tool, goal, session, start directory and time; that record is the join from a slug to a transcript, and it currently records no id for Codex
- packages/reggie/src/claim.ts because the claim file carries the session field, filled from the launcher's minted id or from `sessionName`, and a claim made from inside a session is the other place the real id has to land
- packages/reggie/src/cli.ts because the `journal` command group gains `derive`, and the existing `--session` option on `journal add` documents the suffix that nothing sets
- packages/reggie/src/history.ts because commits by task, and a completed task's commits from its merge commit, are what derive narrates for the commit half; this is the seam with `task-attribution-by-merge`
- packages/reggie/src/tasks.ts because the state transitions derive narrates, claim, plan, packet, verdict, release, are derived there from branches, packets and pull requests
- packages/reggie/src/packet.ts because the completion packet and its evidence folder are the evidence a derived entry should link, and `decidePacket` already appends its own journal entry at the moment of a verdict
- packages/reggie/src/context.ts and packages/reggie/src/docs.ts because the working agreement at the foot of every context pack and the generated instruction block are where sessions are asked to write an entry per step, and that request changes once entries are derived
- packages/reggie/src/serve.ts and packages/reggie/src/mcp.ts because they are the other journal writers, the journal view links entries to evidence and plan files by id, and the later serve pass would call the same function the verb wraps
- .reggie/.cache/launches because the launch records are read, not only written, once derive exists, and they may need a Codex-side handle they do not carry today
- packages/reggie/src/journal.test.ts and a fixture transcript for each tool, because the decision's reason for a verb over a hook is that a verb can be tested against a fixture transcript
- The home `.claude/projects` and `.codex/sessions` folders, which are read-only inputs outside the repo and outside git, and whose layout on this machine does not match the note yet

## Open questions
- How is the listener-register prose produced: a headless model call over the transcript (the 2026-09-13 decision allows `claude -p` and `codex exec` as a tool use with an input and an output) or a deterministic template over the facts Reggie already has (commits, transitions, the session's closing messages)? A model call gives real prose and costs money, needs the network, and is hard to assert on; a template is testable against a fixture and free but reads like a log. The 2026-09-15 reason for a verb, that it can be tested against a fixture transcript, pulls toward the template or toward a model call whose input is the testable part.
  > Answered by jacobpress on 2026-09-15: Template by default over commits, transitions and the closing assistant turns, with an opt-in flag that makes one headless model call over the same assembled facts. Free, offline, testable against a fixture.
- What are "the session's own summary messages" in each transcript format: the assistant's final turns, everything after the last tool call, the messages that name the packet, or a compaction summary the tool wrote itself? Claude transcripts carry tool calls, tool results and several message types; which of them derive reads decides how much of the format Reggie has to understand.
- Where does the transcript actually live for a launched session on this machine? The worktree's project folder holds a session-id folder with a `workflows` folder inside and no flat transcript file, which is not the path the intake note gives; and a session started in `packages/reggie` encodes to a different project folder than one started at the root, so derive may have to search every folder whose decoded path is inside the repo.
- Which file does a derived entry go into: the person-and-session day file that hand entries use, a slug-named file (the naming the union-merge item explicitly deferred), or a derived-only file per task? And once `sessionName` carries the real id, is one day file per session id acceptable, since it turns the day folder into many small files?
  > Answered by jacobpress on 2026-09-15: The existing day file with the real session id in its name, one file per session; no slug-named files.
- How does derive know what an earlier entry already said, so re-running it for a task in flight appends only what is new? A watermark per task (last transcript position and last commit covered) has to live somewhere, in the entry itself, in the launch record or in the task folder, and each of those survives a merge and a branch release differently.
- How is a Codex session matched without a minted id: by the working directory in its session metadata plus a time window from the launch record or the claim date? What happens when two Codex sessions ran in the same worktree, when a session was forked or resumed (the metadata carries a forked-from id), or when a session was started by hand with no launch record at all?
- Does derive cover shaping and planning sessions, which never claim a branch and leave no commits, or only build sessions on a task branch? The shaping sessions on 2026-09-15 wrote the most useful entries so far, and the discuss session the idea action will launch has the same shape.
  > Answered by jacobpress on 2026-09-15: All launched sessions for the slug, whatever their goal; a session without commits derives from its transcript and the transition it produced.
- Who is the person on a derived entry: the launch record's person, the claim file's person, the commit author, or the current person from `people.yaml`? A task built by one person and merged by another has two answers.
- Which transitions does derive narrate, given that `decide` already appends an entry at the moment of a verdict and `claim` and `release` append theirs? Narrating them again from the transcript double-tells the story; skipping them leaves derive to narrate only what happened between.
- What does a derived entry link as evidence: commit shas, the packet, the files under the task's evidence folder, and does the transcript path count, given that it is outside the repo and specific to one machine?
- What does derive do when the transcript is gone but the commits remain, which will be the state of every task landed before this ships and of any task old enough to fall outside the tool's retention: write a commits-only entry, or refuse and say why?
- Is the `sessionName` precursor part of this task, landed first as its own small slice, or already owned by the journal-collision item, whose brief lists the same function under its suspected area?
  > Answered by jacobpress on 2026-09-15: Its own small slice, landed before this task: captured as session-name-reads-real-id.
- For a completed task, does derive re-find the merge commit by walking the base branch, or read a merge sha recorded when `decide` merged? The attribution brief left that open and derive is the consumer that needs the answer.
- Does the verb print the entry for review before appending, or append and report? Once the serve pass calls it the answer is append, but the first weeks are the period in which it is not yet trusted.
- What does derive do in team mode, where the transcript is on the machine that ran the session and the serving checkout may be another? Commits-only on other machines is one answer; a transcript summary committed beside the packet is another.
- When does the generated instruction block stop asking sessions for one entry per step: in this task, once derive exists, or only once the serve pass is trusted and hand entries become the exception?

## Not this
- The pass inside `reggie serve` that calls derive on its own. The decision defers it until the verb is trusted; this task builds the verb and the function it wraps, and leaves the schedule and the trigger to a later item.
- A session-end hook. Rejected on 2026-09-15 because a hook is per machine and Codex has none; nothing here installs into either tool's hook configuration.
- The `.gitattributes` union line for journal files. That is `journal-files-conflict-on-merge-a-claim-in-the-m`, which lands before this and stops the collision; this item is what eventually makes the collision go away, not the line that papers over it.
- Naming journal files by task slug. The naming decision was explicitly deferred with the union line; if derive needs a file of its own that is an open question here, not a rename of the existing scheme.
- Joining commits to tasks and performing the merge. That is `task-attribution-by-merge`, which this depends on for completed tasks; derive consumes the lookup it builds and does not add another.
- Parsing `Co-Authored-By` into per-commit coauthors. It reads the same commit bodies, but its question is who wrote a file; a derived entry attributes the session, not each line.
- Episodes, narration and the voice loop. They read the journal once it exists and are their own milestones; nothing here composes audio or a daily story.
- Reading transcripts for anything but the journal: session search, cost, or a transcript view in the web UI would all reuse the transcript reader, and none of them is in scope.
- Changing what a hand-written entry looks like or how the journal view renders entries. Hand entries stay allowed and stay in their format; derive writes entries the existing reader already parses.
